# 여러 사업장 SaaS 운영 전환 점검

작성일: 2026-10-13 · 기준 커밋: `805dbcb` 및 현재 문서 정리 변경분

목표는 서로 다른 사업장이 가입해 사용하는 예약 운영 SaaS예요. 현재 UI·디자인 토큰·업무 시나리오는 재사용할 수 있지만, 데이터 저장·인증·권한·예약 처리·메시지 발송·AI 실행은 새로 구현해야 해요. **화면 47개를 만든 상태와 서비스 운영 준비가 된 상태는 구분해야 해요.**

권장 순서는 **사업장 격리와 인증 → 수동 예약 운영 → 알림과 장애 복구 → 승인형 AI → 제한적 자동화**예요. 여러 사업장을 지원하는 구조를 처음부터 만들고, 실제 도입은 소수 사업장부터 넓혀요.

10/13 후속 결정: 멀티테넌트로 진행해요. 테넌트·지점 경계와 구체적인 격리 기본안은 [멀티테넌트 아키텍처 설계](MULTITENANT_ARCHITECTURE.md)에 정리했어요. 후속 작업에서 공급자 독립적인 DB·RLS·소속 검사·지점 서비스 기반을 구현했어요([현재 아키텍처](ARCHITECTURE.md)). 아래 결손 목록은 기반 구현 전 점검 기록이에요. 실제 로그인·예약·AI 등 운영 기능은 여전히 남아 있으며 DB·인증 공급자는 미정이에요.

## 1. 점검 범위와 현재 상태

저장소의 라우트, 주요 컴포넌트의 상태 변경, 샘플 데이터와 정책, 패키지·설정·문서를 정적으로 점검했어요. Figma·manyfast의 최신 원본, Vercel/GitHub 계정 설정과 실제 서비스 부하·침투 테스트는 이번 범위에 포함하지 않았어요. 아래의 ‘없음’은 이 저장소에서 구현을 확인하지 못했다는 뜻이에요.

| 영역 | 확인한 상태 | 운영 전환 판단 |
| --- | --- | --- |
| 프런트엔드 | Next.js 16.3.8, React 19.2.8, TypeScript, Tailwind v4 | 현재 기반 유지 가능 |
| 화면 | `page.tsx` 51개. 업무 화면 집계는 47개이고 소개·대체 경로·리다이렉트 포함 여부가 달라요 | 화면 수로 기능 완성도를 판단하면 안 돼요 |
| 데이터 | `src/data/` 14개 샘플 파일 | 테스트 fixture로 보존하고 운영 조회를 DB로 교체 |
| 서버 업무 처리 | Route Handler 0개. `use server` 업무 함수·DB 접근·인증 구현 없음 | Next.js 서버 렌더링은 있지만 업무 백엔드는 없음 |
| 변경 저장 | 예약·출석·문의·설정 등이 컴포넌트 `useState`를 변경 | 새로고침·화면 이동·다른 기기에 일관되게 반영되지 않음 |
| AI | 규칙 기반 고정 답변, 샘플 제안·근거·성과 수치 | 모델 연결·평가·실행 제어 필요 |
| 품질 | 이번 대화의 앞선 점검에서 타입 검사·린트 통과 | 업무 정확성·보안 검증과는 별개 |
| 빌드 | 폰트 다운로드 실패 후 권한을 높여 재시도했으나 Turbopack 포트 생성 권한 제한으로 미완료 | CI에서 재현 가능한 프로덕션 빌드 확인 필요 |
| 자동 테스트·CI | 테스트 스크립트·테스트 스위트·`.github/workflows` 없음 | 핵심 업무 통합 테스트부터 추가 |

이번 작업은 점검과 설계 제안이에요. 제품 코드·DB·외부 서비스 설정을 변경하지 않았어요.

`WaitingCard`의 자동 확정 기본 표시가 `true`인 것은 현재 김하늘이 이미 동의한 샘플 시나리오와 맞아요. 이를 단순히 버그로 바꾸기보다 운영에서는 저장된 회원별 동의를 읽어야 해요. 새 동의 입력은 기존 결정대로 기본 꺼짐을 유지해요.

### 4.2 SaaS 구독과 회원 결제를 분리

기존 결정의 ‘이용권·결제 없음’은 사업장이 회원에게 수업료를 받는 기능에 대한 범위예요. **사업장이 이 SaaS 사용료를 내는 구독은 별도 기능**으로 설계해야 해요. 기존 결정을 묵시적으로 뒤집지 않아요.

- SaaS 구독: 플랜·체험 기간·구독 상태·청구 주기·해지·결제 실패·유예·영수증/청구 내역·서버 기능 권한을 정의해요. 유료 셀프서비스 공개 전에는 결제 공급자 연결과 중복/지연 웹훅 처리가 필요해요.
- 초기 계약형 도입: 수동 청구는 가능하지만 서버의 플랜/사용량/만료 상태와 변경 감사는 처음부터 필요해요. 결제 UI 자동화만 나중으로 미뤄요.
- 사용량: 조직별 AI 호출·토큰·메시지·저장 용량 집계, 경고·한도·예산 차단. AI 예산 소진이 예약·취소 같은 핵심 수동 업무까지 막으면 안 돼요.
- 회원 결제/이용권: 기존 범위대로 보류 가능. 단, 유료 수업을 누가 신청할 수 있는지 운영 모델은 결정해야 해요. 외부 결제 확인 또는 직원 확인이 필요하다면 최소한의 ‘예약 가능 자격’ 검사가 필요하고, 횟수 차감·환불·정산까지 필요하면 별도 범위로 확정해요.

## 5. 권장 아키텍처

초기에는 **Next.js 웹 앱 + 모듈별 업무 서버 코드 + 관리형 PostgreSQL + 영속 작업 큐/워커**를 권장해요. 서비스를 여러 개로 쪼개기보다 데이터 정합성과 운영 관찰 가능성을 먼저 확보해요. 워커는 웹 요청과 다른 수명으로 실행하되 같은 도메인 코드를 공유할 수 있어요. 공급자·지역·요금제는 데이터 처리 조건과 예상 사용량을 비교한 뒤 확정해요.

```text
관리자 PC / 관리자 모바일 / 회원 / 공개 문의
                      ↓
Next.js 읽기 화면 · Server Actions · Route Handlers
                      ↓
인증 → 조직·지점·객체 권한 → 입력 검증 → 업무 서비스
                      ↓
PostgreSQL 트랜잭션
  예약·회차·동의·승인·실행·감사 + 발송/작업 예정 기록(outbox)
                      ↓
영속 큐/워커 → 메시지 공급자 · 제한된 AI 작업 · 외부 연동
                      ↑
공급자 웹훅 → 서명·중복 검사 → 처리 상태 저장

공통: 조직별 사용량·속도 제한 / 오류·지연 알림 / 백업·복구
```

Next.js 가이드는 서버 데이터 접근 계층에서 권한을 검사하고, 클라이언트에 필요한 데이터만 반환하도록 안내해요. 페이지나 layout 검사만으로 모든 변경 요청을 보호할 수는 없어요. 설치된 패키지의 `node_modules/next/dist/docs/01-app/02-guides/data-security.md`와 [공식 인증 가이드](https://nextjs.org/docs/app/guides/authentication)를 함께 기준으로 삼아요.

예약 변경과 발송 예정 기록을 같은 DB 트랜잭션에 넣으면, 예약만 저장되고 발송 요청이 사라지는 문제를 줄일 수 있어요. 이 outbox 방식도 전달 중복은 생길 수 있으므로 소비자 멱등 처리가 필요해요. [AWS outbox 가이드](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)

Cron은 만료·재처리 대상 탐색의 시작 신호로 쓰고, 업무 진행 상태는 DB에 남겨요. Vercel Cron은 실패 호출을 자동 재시도하지 않으며 중복 실행을 고려해야 하므로, Cron을 추가하는 것만으로 발송 신뢰성이 생기지는 않아요. [Vercel Cron 운영 문서](https://vercel.com/docs/cron-jobs/manage-cron-jobs)

### 5.1 코드 구조 제안

```text
src/app/                 경로, 서버 조회, 얇은 action/handler
src/components/ui/       기존 토큰과 표현 컴포넌트
src/features/            예약·출석·문의·승인의 화면과 폼
src/domain/              상태, 정책, 값 검증, 서버와 공유할 타입
src/server/auth/         세션·재인증
src/server/access/       조직·지점·객체 권한
src/server/services/     예약·이동·휴강·승인 업무
src/server/repositories/ 조직 범위가 필수인 DB 접근
src/server/integrations/ AI·메시지·결제·OAuth 공급자 어댑터
src/jobs/                재시도 가능한 작업과 스케줄러
src/demo/                기존 샘플 시나리오와 데모 어댑터
db/                     스키마·마이그레이션·개발용 seed
tests/                  정책·DB 통합·격리·E2E 테스트
```

전역 상태 관리 라이브러리를 먼저 넣는 것으로 저장·정합성 문제를 해결하려 하지 않아요. UI 입력 상태는 `useState`로 유지하고, 업무 상태의 정본은 서버에 둬요. PC와 모바일의 승인·출석 로직은 같은 서비스와 상태 정의를 사용해요. `src/data`가 UI 컴포넌트 타입을 import하는 의존 방향도 도메인 타입 중심으로 정리해요.

### 5.2 데이터 경계

`tenant`는 독립 계약 고객인 조직/브랜드 운영 단위, `branch`는 그 내부 지점이에요. 같은 테넌트의 브랜드·지점 공유 범위도 명시해요. SaaS 운영사 직원은 사업장 ‘최고관리자’와 다른 역할이에요.

- 공유 DB·공유 스키마로 시작하되 업무 테이블에 `tenant_id`를 두고, 필요한 테이블에는 `branch_id`도 둬요. `(tenant_id, id)` 참조 등으로 다른 조직의 레코드를 잘못 연결하는 것도 막아요.
- 브라우저가 보낸 `tenant_id`·지점·역할을 신뢰하지 않아요. 로그인한 사용자의 활성 소속과 객체 권한을 검사해요. 백그라운드 작업·검색·내보내기도 동일해요.
- RLS를 방어 계층으로 사용할 수 있어요. 소유자/우회 권한 계정은 정책을 우회할 수 있으므로 앱 계정 권한·연결 풀의 트랜잭션별 조직 컨텍스트·서비스 계정을 함께 검증해요. [PostgreSQL RLS 문서](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)
- 캐시 키와 무효화 키에 조직·지점·필요한 권한 범위를 포함해요. 회원별 응답과 토큰 기반 문의 화면을 공개 공유 캐시에 저장하지 않아요. 파일 다운로드도 조직 소속 검사 뒤 짧은 만료 링크로 제공해요.
- 전역 로그인 계정과 조직별 고객 프로필을 분리해요. 같은 전화번호/계정이 두 사업장을 이용해도 한 사업장이 다른 사업장의 방문·메모를 볼 수 없어야 해요.
- 지원 접근은 사유·허용 범위·만료 시간·감사 기록을 갖춰요. 데이터 내보내기·대리 변경은 별도 권한과 재인증이 필요해요.

이는 논리 모델 초안이에요. 각 테이블의 상세 필드·색인·참조·이관 정책을 확정한 ERD는 후속 설계가 필요해요.

### 5.4 API와 업무 명령 계약

내부 웹 변경은 Server Action, 공급자 webhook·공개 API는 Route Handler로 시작할 수 있어요. 둘 다 같은 인증/권한·업무 서비스를 호출하고, 요청 본문의 사용자·역할을 행위자로 기록하지 않아요.

| 업무 | 최소 명령/조회 계약 |
| --- | --- |
| 회차 | 생성·반복 생성·변경·휴강, 기간/지점별 조회. 수정에 `expectedVersion` 포함 |
| 예약 | 신청·확정·거절·취소·이동 요청. `sessionId`, 참여자, 멱등 키, 필요한 동의 버전 |
| 대기·출석 | 대기 등록/철회/동의 변경, 출석 일괄 기록. 예약 ID와 수정 버전으로 대상 지정 |
| 승인 | 제안 조회·수정 버전 생성·승인·거절. 승인한 `proposalRevisionId`를 실행에 결합 |
| 실행 | `executionId`로 현재 단계·완료/실패 결과 조회. 재시도는 허용된 실패 단계만 |
| 공개 문의 | 접수·링크 교환·추가 메시지·재발급. 일반 관리자/회원 API와 접근 범위 분리 |
| SaaS | 초대/철회·지점 배정·플랜 권한·사용량 조회·구독/해지·데이터 내보내기/삭제 |

응답은 성공 값 외에 `FORBIDDEN`, `SOLD_OUT`, `DEADLINE_PASSED`, `VERSION_CONFLICT`, `APPROVAL_EXPIRED`, `CONSENT_MISSING`, `RATE_LIMITED`처럼 UI가 다음 행동을 정할 수 있는 오류를 정의해요. 외부 처리 지연은 ‘접수됨 + 작업 ID’를 반환해요. 공개 오류에는 다른 고객의 존재나 원문 DB 오류를 넣지 않아요. 목록은 커서/페이지·기간·정렬을 제한하고, 알림/승인 상태는 우선 주기 조회로 갱신한 뒤 필요한 부분에만 실시간 구독을 추가해요.

## 6. 예약과 승인에서 서버가 보장할 규칙

### 6.1 상태를 분리

- 회차: 예정 / 진행 중 / 종료 / 휴강.
- 예약: 신청 대기 / 확정 / 거절 / 만료 / 취소. 대기 신청은 별도 엔터티로 관리해요.
- 출석: 미확인 / 출석 / 노쇼. 예약 상태나 시간 경과로 자동 출석시키지 않아요.
- 승인: 대기 / 승인 / 거절 / 만료 / 대체됨. 실제 실행의 성공 여부와 구분해요.
- 실행: 접수 / 실행 중 / 성공 / 일부 실패 / 실패 / 결과 확인 필요.
- 메시지: 대기 / 공급자 접수 / 전달 확인 / 실패 / 차단 / 결과 확인 중. ‘발송 요청 성공’과 ‘수신자에게 전달됨’을 구분해요.

### 6.2 정원과 변경

동일 회차의 모든 확정 경로가 동일한 잠금·트랜잭션 규칙을 사용해야 해요. 회원 직접 신청, 관리자 확정, AI 승인 실행, 대기 자동 확정이 각각 다른 정원 계산을 쓰면 안 돼요. PostgreSQL 행 잠금은 같은 행을 수정하려는 다른 트랜잭션을 대기시키므로 회차별 정원 판단에 사용할 수 있어요. 이동은 두 회차를 일정한 순서로 잠그고 교착/직렬화 실패 재시도를 설계해요. [PostgreSQL 잠금 문서](https://www.postgresql.org/docs/current/explicit-locking.html)

확정 수는 예약 참여자에서 도출하거나, 같은 트랜잭션에서 갱신하는 카운터로 유지해요. 화면용 `booked`와 명단을 따로 손으로 갱신하지 않아요. 2자리 요청이면 2자리가 모두 가능한지 확인하고, 일부만 확정하는 정책은 별도로 동의를 받아야 해요.

예약 이동은 자동 확정일 때 새 자리 확보와 기존 예약 취소를 한 트랜잭션으로 처리해요. 관리자 확인이면 변경 요청만 만들고 기존 예약을 유지한 뒤, 승인 시 같은 검사를 실행해요. 거절·만료·충돌 시 기존 예약은 유지돼야 해요.

### 6.3 승인 실행 순서

1. 서버에서 로그인·조직·지점·승인 권한과 승인 대상 버전을 확인해요.
2. 승인할 행동·수신자·메시지 본문·근거 시각·정책 버전을 저장해요. 수정한 제안은 새 버전으로 만들어요.
3. 실행 직전에 현재 권한, 승인 만료, 회차 상태·정원, 예약 상태·중복, 발송 동의·연결 상태를 다시 확인해요.
4. 짧은 DB 트랜잭션에서 예약 변경·감사 기록·outbox를 함께 저장해요. 외부 LLM/메시지 호출을 기다리면서 DB 잠금을 유지하지 않아요.
5. 워커는 이미 완료된 단계는 건너뛰고 미완료 단계만 처리해요. 예약 성공·메시지 실패라면 메시지만 재시도해요.
6. 응답이 끊겨 결과를 모를 때는 기존 실행 ID로 조회해요. 새 예약 작업을 다시 만들지 않아요.

멱등 키는 조직·사용자/행위·요청 내용에 결합하고 같은 키로 다른 내용을 보내면 거절해요. DB 효과는 한 번만 만들도록 보장하고, 외부 발송은 공급자 중복 키·상태 조회·웹훅으로 조정해요. 공급자가 중복 방지/조회 기능을 제공하지 않으면 ‘정확히 한 번 전달’을 약속하지 않고 애매한 결과를 운영자가 확인하도록 해요.

### 6.4 구현 전 확정할 정책 충돌

| 정책 | 결정이 필요한 내용 |
| --- | --- |
| 신청 대기의 자리 | AI 제안이 자리를 점유하지 않는 결정은 있음. 회원의 관리자 확인 신청이 자리를 점유하는지, 언제 만료되는지 명시 |
| 취소 24시간과 참석 확인 | ‘못 가요’ 예외는 기존 결정으로 유지. 해당 회원·예약·유효한 참석 확인·수업 시작 전 여부를 서버에서 검사. 전체 취소 정책을 사실상 우회하는 상품 경험이 의도인지 검토 |
| 대기 순서 | 자동 확정 동의자 우선 배정과 알림 후 선착순이 섞일 때의 우선순위·시간 경계·취소 재진입 순번 결정 |
| 3시간/1시간 규칙 | 자동 확정 가능한 마지막 시각, 확정 후 취소 허용 시각을 서버에서 계산. 신청 마감과 충돌할 때 우선순위 정의 |
| 프로그램 변경 | 변경된 정원·길이·취소 정책이 기존 회차/예약에도 적용되는지, 미래 회차부터 적용되는지 명시 |
| 출석 기록 시작 | 문서의 ‘시작 후’와 현재 UI의 ‘종료 후’ 중 실제 운영 규칙 확정 |
| 수신 동의와 필수 안내 | 광고·운영 안내·인앱 알림·직접 연락을 구분하고 전문가 검토. 동의 거부자도 필요한 공지를 앱에서 볼 수 있게 함 |
| AI와 외부 개인정보 | ‘외부 앱 전송 금지’ 문구와 허용된 메시지·LLM 위탁 처리 경계 구체화. 무허가 내보내기 금지와 정당한 처리 계약을 구분 |
| 회원 예약 자격 | 이용권 없이 누구나 자동 확정해도 되는지. 기존 고객 확인·체험·전화 예약·동반자 처리 결정 |

## 7. AI를 운영 기능으로 만드는 조건

첫 AI 기능은 문의 답변 초안·고객 요약·예약 제안 정도로 한정하는 편이 좋아요. 기존의 ‘AI 제안 → 사람 승인’ UX는 유지하되 실제 권한 제어는 서버에서 수행해요.

- **입력 범위**: 해당 조직·지점·고객에게 허용된 자료만 검색. 검색/벡터 저장소도 테넌트 격리. 연락처·자유 메모 등 불필요한 개인정보는 모델에 보내지 않아요.
- **출력**: 구조화된 제안 스키마를 검증하고, 모델이 만든 회원/회차 ID·잔여석·위험 등급을 그대로 신뢰하지 않아요. 도구 목록은 허용된 업무만 제공해요.
- **실행**: 모델은 SQL·임의 URL·관리자 권한을 직접 실행하지 않아요. 예약을 바꾸려면 6장의 동일한 업무 서비스를 거쳐요. 회원 본인 확인과 사업자 승인 주체도 구분해요.
- **근거**: 근거 문서 ID/버전·조회 시각을 저장하고 없으면 답변을 유보해요. 원문 속 지시를 시스템 정책으로 취급하지 않아요.
- **평가**: 잘못된 날짜·정원 초과·수신 거부·다른 조직 조회·지시 조작·오래된 정책·부분 실패 사례를 회귀 평가해요. Test A는 카드 UX 검증이며 AI 정확성/보안 평가는 별도로 필요해요.
- **운영**: 모델/프롬프트 버전, 지연·비용·오류, 제안 채택·수정·거절 이유를 수집해요. 조직별 예산, 동시 실행 제한, 기능별 긴급 중지와 수동 처리 경로를 마련해요.
- **자동화 확대**: 리마인드처럼 정해진 규칙으로 처리할 일은 결정적 스케줄러를 사용해요. AI 업무의 자동 실행은 낮은 위험·허용된 범위에서만 열고 기존 가드레일을 유지해요.

LLM의 과도한 권한과 자율 실행은 피해를 키우므로 도구 범위를 줄이고 실제 권한을 후단 시스템에서 강제하는 방향이 적절해요. [OWASP Excessive Agency](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/)

## 8. 보안과 개인정보

공개 문의는 가입 없는 접근이므로 일반 회원 API와 다른 보호가 필요해요. 토큰 원문 대신 해시를 저장하고, 조직·문의·허용 행동·만료를 묶어요. 재발급 시 기존 링크 철회 정책, 전화번호 변경, 링크 전달/유출 시 대응을 정해요. 현재 30일 유효 정책은 개인정보 범위와 함께 재검토하고, 예약 변경처럼 민감한 행동은 추가 확인을 고려해요.

응답으로 문의/계정 존재를 노출하지 않고, 발송·조회에 서버 속도 제한을 적용해요. 토큰 URL은 분석 도구·로그·Referer로 남기지 않도록 다루고, 가능하면 검증 후 제한된 세션으로 교환해 깨끗한 URL로 이동해요. 예측 불가능한 토큰·만료·존재 비노출·속도 제한의 원칙은 [OWASP 토큰 기반 복구 가이드](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html)를 참고할 수 있어요. 문의 링크의 수명주기는 별도로 설계해요.

추가 구현 항목은 다음과 같아요.

- 세션 쿠키 보호, 요청 출처/CSRF 대응, 입력 길이·형식·본문 크기 제한, 서버 검증, CSP 등 보안 헤더. 실제 Vercel 제공 헤더와 겹침도 확인해요.
- OAuth 토큰·메시지/결제/LLM 키를 서버 비밀 저장소에 보관하고 교체·철회 절차를 둬요. 운영·스테이징 키와 발송 계정을 분리해요.
- 웹훅의 서명·시간·중복 이벤트를 검증하고, 조직은 검증된 공급자 연결에서 찾도록 해요.
- 사진 첨부를 제공하면 크기·형식·악성 파일 검사·비공개 저장·권한 있는 다운로드가 필요해요. 준비 전에는 옵션을 노출하지 않아요.
- 사업장과 SaaS 운영사의 개인정보 처리 역할, 위탁/재위탁, 실제 LLM 처리 국가·보유·학습 조건, 데이터 접근 담당자를 확정해요.
- 수집 항목·목적·보관 기간·동의/철회·문의처·처리방침 버전을 기록해요. Test A의 녹화/연락처 보관 기간을 운영 회원 데이터에 재사용하지 않아요.
- 탈퇴·조직 해지 시 원본 DB뿐 아니라 파일·검색 색인·AI 저장 데이터·캐시를 함께 정리해요. 감사 이력은 필요한 최소 정보로 유지하고 백업 만료·복원 후 재파기 절차도 정의해요.
- 필라테스 문의에 건강·부상 정보가 들어갈 수 있어요. 자유 메모 수집 범위를 줄이고 실제 처리 요건을 전문가와 검토해요.

구체적인 적법 근거와 기간은 데이터 흐름과 계약을 확정한 뒤 전문가 회신으로 마무리해야 해요. 처리방침은 [개인정보보호위원회 공식 안내서](https://pipc.go.kr/np/cop/bbs/selectBoardList.do?bbsId=BS217&mCode=D010030000)를 기준으로 점검해요.

## 9. 운영용에서 제거하거나 교체할 것

| 제거·교체 대상 | 처리 방법 |
| --- | --- |
| `?as=admin`, 보는 사람 전환, `?state=`, `?step=result` 등 상태 체험 장치 | 데모에만 보존. 운영의 권한·결과는 서버가 결정 |
| 타이머/로컬 상태 기반 ‘실행 완료’ | 서버 처리 상태와 작업 ID로 교체 |
| 고정 사람·브랜드·날짜·잔여석·성과 | 조직 데이터 또는 빈 상태로 교체. 샘플이 운영 번들에 섞이지 않도록 검사 |
| 실제 기능 없는 버튼·필터·모듈 | 구현 완료 전 운영에서 숨기거나 명확한 지원 범위 표시 |
| QR 예시·인증 건너뛰기·가짜 연결/내보내기 | 실제 동작으로 교체하거나 기능 제공을 보류 |
| 서버 동작 없는 ‘발송했어요·기록했어요·실시간’ | 사실에 맞는 접수/실패/확인 중 문구 |
| 무제한 민감도 조절·자동 실행 확대 UI | 실제 평가된 설정만 제공. 끌 수 없는 정책은 서버 상수/정책으로 유지 |
| 운영 홈의 포트폴리오·케이스 스터디 | 기존 공개 데모는 유지하고 서비스 앱과 배포·데이터·쿠키 경계 분리 |

포트폴리오 자산과 샘플을 삭제할 필요는 없어요. 운영과 데모의 환경·진입점·DB·발송 키를 분리하는 것이 핵심이에요. 운영 환경에서 `NEXT_PUBLIC_*` 토글 하나로 데모 권한 우회가 다시 활성화되는 구조는 피해야 해요.

## 10. 배포와 품질 관리

### 10.1 출시 전 운영 기반

- CI: 고정된 Node 버전과 lockfile로 `npm ci` → 타입 검사 → 린트 → 정책/DB 통합 테스트 → 프로덕션 빌드 → 주요 E2E. 보호된 main과 필수 검사·배포 승인 정책은 저장소 설정에서 확인/적용해요.
- 환경: 공개 데모, 내부 스테이징, 운영을 분리. 미리보기 배포가 운영 DB·고객 발송 키를 쓰지 않게 해요. 테스트 발송은 허용 목록에만 가능하게 해요.
- DB: 버전 관리된 마이그레이션·스키마 호환 배포·연결 풀·색인·느린 쿼리 관찰. 백업을 켜는 것에 더해 별도 환경에 실제 복원해요.
- 복구 목표: 데이터 유실 허용 범위(RPO)와 복구 시간(RTO)를 정하고 모의 장애로 측정해요. 금액·SLA를 정하기 전 고객 요구와 운영 비용을 함께 판단해요.
- 관측: 요청/실행/이벤트 ID로 웹→DB→워커→발송 추적. 개인정보·토큰은 로그에서 제거하고 오류율·예약 실패·큐 지연·메시지 실패·AI 비용에 알림을 설정해요.
- 스케일: 페이지네이션·날짜 범위 제한·색인, 조직별 동시 작업 제한과 큐 공정성. 한 사업장의 대량 발송이 다른 사업장의 예약 응답을 막지 않게 해요.
- 장애 대응: AI/메시지 기능 중지, 실패 건 조회·재처리, 발송 결과 대사, 담당자 수동 처리, 고객 공지 절차를 마련해요.
- UI: 저장 중 이중 클릭 방지, 실패 시 입력 보존, 충돌 시 최신 값 비교, 미저장 이탈 안내, 접근성·모바일 키보드·느린 네트워크 점검. 로컬 컴포넌트 상태만 바꾸는 낙관적 성공은 중대한 작업에 사용하지 않아요.

### 10.2 의존성 검사 결과

2026-10-13 `npm audit --json` 결과 high 5개, `npm audit --omit=dev --json` 결과 알려진 취약점 0개예요. high 5개는 서로 독립적인 5개 취약점이 아니라 `braces`의 중첩 패턴 서비스 거부 취약점이 개발 도구 의존 경로에 전파된 결과예요.

`eslint-config-next → @next/eslint-plugin-next → fast-glob → micromatch → braces`

공식 advisory는 [GHSA-vfj7-8cjw-p6xm](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm)이에요. 현재 감사 도구의 자동 수정 제안은 `eslint-config-next@14.2.35`로 바꾸는 것이므로 Next 16 프로젝트에 그대로 적용하지 않아요. 호환되는 상위 릴리스·공식 패치 가능성을 확인하고 개발/CI 노출 범위를 평가한 뒤 조치해요. 운영 의존성 0건은 인증·권한·업무 로직이 안전하다는 보증은 아니에요.

| 2. 수동 예약 완성 | 프로그램·강사·공간·회차 생성, 회원 신청·관리자 확정·변경·취소·출석·휴강 | 고객이 신청하고 사업자가 처리한 결과가 모든 화면에 일치, 동시성 테스트 통과 |

| 4. SaaS 제공 | 온보딩·CSV 이전·조직별 링크, 플랜·사용량·청구 또는 계약 관리, 지원 도구 | 소수의 독립 사업장이 직접 시작하고 운영 가능. 유료 셀프서비스 전 결제 수명주기 완성 |
| 5. 승인형 AI | 문의 초안·요약 → 예약 제안·승인. 근거·정책 검증·평가·비용 차단 | 실제 데이터 평가와 공격/실패 시나리오 통과, AI 없이도 업무 지속 |
| 6. 확대 | 제한적 자동화, 외부 연동, 분석, 추가 업종 | 관측된 수요·품질·비용에 근거해 기능별 개방 |

지금 바로 만들 첫 구현 단위는 **두 조직 생성 → 소유자/직원 로그인 → 프로그램·회차 생성 → 회원 신청 → 관리자 확정 → DB 저장과 활동 기록 → 양쪽 화면에서 같은 예약 확인**이에요. 그 다음 취소·이동·동시성·메시지 실패를 붙여 작은 운영 단위를 완성해요.

유지할 것은 디자인 토큰·공통 UI·한국어 문구·승인 중심 UX·일부 실패를 보여 주는 설계예요. 크게 바꿀 것은 클라이언트 중심 업무 처리와 분산된 샘플 모델이고, 새로 만들 것은 조직 격리·인증·업무 서버·신뢰 가능한 작업 실행·SaaS 수명주기예요.
