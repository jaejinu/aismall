# 로그인·첫 조직 생성

2026-10-14 구현 범위예요. [현재 아키텍처](ARCHITECTURE.md) · [Supabase 설정](SUPABASE_SETUP.md)

## 직접 확인할 흐름

1. 서울 개발 프로젝트의 Authentication → Users에서 **개발용 앱 계정**을 준비해요. Supabase 대시보드 로그인 계정과 별개예요. 이메일 확인이 완료된 사용자만 허용해요. 현재는 회원가입·메일 발송 UI가 없으며 비밀번호를 채팅이나 저장소에 남기지 않아요.
2. `.env.local` 설정과 `npm run db:migrate` 후 앱을 실행해요. 개발 서버 기본은 `http://localhost:3000/login`, 이번 프로덕션 빌드 확인 서버는 `http://127.0.0.1:3300/login`이에요.
3. 이메일·비밀번호 로그인 → `/workspace` → 조직 이름·첫 지점 이름 입력 → `/workspace/[tenantId]`에서 지점을 확인해요.
4. 로그아웃 후 업무 URL을 다시 열면 로그인으로 이동해요. 소속 없는 조직 URL은 404예요.

## 구현과 보안 경계

- `@supabase/ssr` 서버 클라이언트만 사용해요. 로그인·로그아웃은 Server Action POST이고 Next.js의 Origin/Host 검사를 적용해요. 임의 복귀 URL을 받지 않아요.
- `src/proxy.ts`는 `/login`, `/workspace/*`에서 토큰을 갱신하고 요청·응답 쿠키를 함께 갱신해요. 이 경로는 `private, no-store`이며 조직 페이지도 동적 렌더링해요.
- 쿠키는 HttpOnly·SameSite=Lax, 프로덕션은 Secure예요. 브라우저에서 Supabase 클라이언트를 사용하지 않아요. 브라우저 클라이언트를 추가할 때는 이 결정을 함께 검토해야 해요.
- 매 요청의 `getUser()`로 인증 서버의 사용자 확인 후, `getClaims()`의 서명 검증 결과에서 issuer·subject·만료를 대조해요. 이메일 인증 전 사용자와 익명 계정은 거부해요. 이메일이나 사용자 수정 가능한 metadata로 ID·역할을 결정하지 않아요.
- `resolve_identity`는 검증된 issuer/subject를 내부 UUID에 연결해요. 정지된 사용자를 재활성화하지 않아요. 로그인 자체는 조직 접근을 허용하지 않아요.
- `my_organizations`는 해당 사용자의 활성 조직·소속만 반환해요. 실제 지점은 기존 `withTenant`와 RLS로 조회해요.
- `create_first_organization`은 사용자 행을 잠그고 조직·최고관리자 소속·첫 지점·감사·재시도 기록을 원자적으로 생성해요. 동시 제출은 같은 조직을 반환하고 회수된 소속은 되살리지 않아요. 이미 소속 기록이 있는 계정의 추가 조직 생성은 별도 기능으로 남겨요.

`0002_identity_onboarding.sql`의 세 함수는 **SECURITY DEFINER**로 마이그레이션 소유자의 권한을 사용해요. `search_path=pg_catalog` 고정, 전체 스키마명 사용, PUBLIC 실행 금지, `aismall_app`에 함수 실행만 허용해요. 직접 사용자·권한 테이블 쓰기는 계속 금지돼요. 초기 조직 기록은 접근 불가한 `app_private.first_organizations`에 보관해요.

이 함수의 actor/identity 인수는 **검증된 서버 코드만** 지정해야 해요. 서버와 DB 실행 자격 증명은 신뢰 경계이며, 실행 계정 침해·임의 SQL 실행까지 방어하는 기능은 아니에요. Data API 노출이나 클라이언트 입력의 직접 전달을 금지해요. 직원 초대·권한 변경으로 함수를 범용화하지 않아요.

## 검증 결과

- 설정 7개 + PostgreSQL 통합 23개 = 30개 통과. 서명 검증 SDK 호출을 대역으로 제공한 어댑터 거부 테스트, issuer별 ID 분리, 동시 생성 멱등성, 감사 실패 전체 롤백, 정지·소속 회수, 직접 쓰기 차단을 포함해요.
- 서울 개발 DB에 0002 적용. `node scripts/verify-hosted-onboarding.mjs PROJECT_REF`로 실제 runtime·풀러에서 매핑·생성·지점·감사를 확인했어요. 검증은 한 트랜잭션에서 수행하고 롤백하여 데이터를 남기지 않아요. Auth 사용자는 만들지 않아요.
- 타입·린트 통과. 기본 Turbopack 빌드는 환경의 포트 생성 제한으로 실패했지만 `npm run build -- --webpack`은 성공했어요.
- 프로덕션 서버에서 로그인 화면 모바일 390px·데스크톱 1280px 확인, 모바일 가로 넘침 없음. 비로그인 조직 경로 307 → 로그인, `private, no-store`, 잘못된 로그인에 일반 오류 표시 확인.
- **실제 개발 계정으로 사용자가 로그인·첫 조직/지점 생성을 완료했어요.** 이어서 브라우저에서 재진필라테스 조직 선택·광진구점 재조회, 접근 권한 없는 조직 URL 404, 로그아웃 및 기존 지점 주소 재접근 시 로그인 이동을 확인했어요. 새 조직을 중복 생성하거나 사용자 데이터를 삭제하지 않았어요. 토큰 만료 후 갱신·로그아웃 후 재로그인은 아직 직접 검증하지 않았어요.

## 다음 작업

직원 관리 두 계정 E2E → 수동 고객·회차·예약 한 흐름 순서예요. 고객 공개 전에는 회원가입·이메일 확인·비밀번호 복구, SMTP, callback 허용 목록, 앱 단위의 공유 속도 제한·봇 방어, 인증 장애 및 토큰 갱신 브라우저 회귀 테스트가 필요해요. 현재 로그인 오류는 일반화했고 Supabase의 공급자 제한을 따르지만 자체 속도 제한은 아직 없어요. 이메일 링크·OAuth를 사용하지 않아 PKCE callback route는 이번 범위에 없어요.

참고: [Supabase 공식 SSR 가이드](https://supabase.com/docs/guides/auth/server-side/creating-a-client). 이번 변경은 개발 구현이며 공개 배포하지 않았어요. 새 3개 화면의 Figma 대응 프레임은 아직 없어요.

10/14 후속으로 [직원 초대·배정·회수](TEAM_MANAGEMENT.md)를 구현했어요. 초대 이메일 자동 발송·회원가입 UI는 여전히 후속 범위예요. 위 30개는 로그인 구현 당시의 검사 수이고, 현재 전체는 38개예요.

## 회원 계정 진입 (2026-10-14)

로그인 성공 후 고정 경로 `/workspace`에서 운영 소속과 활성 회원 연결을 확인해요. 운영 조직이 있으면 조직 선택, 운영 소속 없이 회원 연결이 있으면 `/workspace/member`로 이동해요. 둘 다 없으면 회원 예약·직원 초대·새 사업장 생성 안내를 보여 줘요. 회원의 명시적 운영 진입은 `?mode=manage`를 쓰며 권한 검사는 기존과 같아요.
