# 멀티테넌트 아키텍처 설계

작성일: 2026-10-13

**멀티테넌트 SaaS로 진행하는 방향은 사용자 결정이에요.** 아래의 테넌트 단위·DB 방식·URL·권한 모델은 그 방향을 구현하기 위한 기본 설계안이에요. 초기 PostgreSQL 스키마·RLS·소속 검사·지점 서비스와 통합 테스트는 구현했어요. 10/14 서버 로그인·내부 사용자 매핑·첫 조직과 지점 생성·조직 선택을 구현했어요. 실제 계정의 기본 흐름은 확인했고 직원 코드 초대·배정·회수까지 구현했고 두 계정의 브라우저 검증과 예약 화면 연결은 남아 있어요. 구현 범위는 [현재 아키텍처](ARCHITECTURE.md), 실행 방법은 [개발 가이드](DEVELOPMENT.md)를 봐요. 아래에는 향후 설계도 포함돼요. 전체 운영 결손과 기능 범위는 [운영 전환 점검](SAAS_READINESS_REVIEW.md)을 함께 봐요.

## 1. 테넌트와 지점의 기준

테넌트는 독립적으로 계약하고 고객 정보를 관리하는 조직/브랜드 단위예요. 지점은 그 테넌트 안의 운영 단위로 두는 것을 기본안으로 삼아요.

```text
AI Small Business OS 운영사
  ├─ 테넌트 A: 재진필라테스
  │    ├─ 강남점
  │    └─ 홍대점
  └─ 테넌트 B: 다른 요가 스튜디오
       └─ 성수점
```

- A와 B는 고객·예약·메모·문의·AI 근거·구독·사용량을 공유하지 않아요.
- A의 최고관리자는 A의 여러 지점을 관리하지만 B에 대한 권한은 없어요.
- 같은 테넌트의 지점 직원도 배정된 지점 업무만 처리해요. 고객이 브랜드 단위 회원이라고 해서 모든 지점의 직원에게 모든 상담·방문 이력을 공개하지 않아요.
- 한 로그인 계정이 여러 테넌트에서 직원이거나 회원일 수 있어요. 로그인 계정은 같아도 소속·역할·고객 프로필은 각각 달라요.
- 단독 매장은 테넌트 1개 + 지점 1개로 표현해요. 화면에서 불필요한 선택기만 감추고 격리 구조는 유지해요.
- 같은 상호의 프랜차이즈라도 계약·고객 정보 관리 주체가 독립되어 있다면 별도 테넌트로 두는 편이 맞아요. 본사 통합 열람은 별도 근거와 권한 설계가 필요해요.
- 첫 버전은 테넌트 하나에 브랜드 하나를 기본으로 해요. 여러 독립 브랜드를 한 계약으로 묶는 상위 그룹은 실제 수요가 있을 때 추가해요.

기존 문서의 ‘최고관리자’는 **해당 테넌트의 최고관리자**예요. SaaS 운영사 지원 직원과 구분해요.

## 2. DB 격리 방식

| 방식 | 특성 | 이 프로젝트 제안 |
| --- | --- | --- |
| 공유 DB·공유 스키마 | 같은 테이블에서 `tenant_id`로 구분. 마이그레이션과 운영을 한 번에 관리하지만 논리적 격리 검증이 중요 | 초기 기본안 |
| 공유 DB·테넌트별 스키마 | 테이블 이름 공간 분리. 스키마별 마이그레이션·접근 경로 관리 증가, DB 장애 자원은 공유 | 초기 채택하지 않음 |
| 테넌트별 DB | DB 연결·백업·자원 단위 분리 가능. 비용과 운영 작업 증가, 애플리케이션 권한 검사는 여전히 필요 | 전용 환경 계약이 필요한 고객에 후속 검토 |

**공유 PostgreSQL + 서버 권한 검사 + RLS(Row Level Security)**를 기본 설계로 제안해요. RLS는 행 단위 DB 접근 제한이에요. 업무 정책을 대신하지 않으므로 정원·마감·승인 권한 검사는 서버 업무 계층에서 함께 수행해요.

PostgreSQL의 테이블 소유자·슈퍼유저·`BYPASSRLS` 역할은 일반 역할과 다르게 RLS를 우회할 수 있어요. 앱 접속 계정과 마이그레이션 계정을 분리하고, 앱 계정에는 DDL·`TRUNCATE`·우회 권한을 주지 않아요. 필요한 테이블에 `ENABLE/FORCE ROW LEVEL SECURITY`와 읽기·쓰기 정책을 검증해요. [PostgreSQL RLS 문서](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)

공유 DB에서는 성능과 장애 범위도 공유돼요. 테넌트별 요청·AI·발송 한도와 큐 공정성이 필요하고, 테넌트 하나의 복원은 전체 백업 복원과 달라요. 초기부터 조직별 내보내기·선택 복구 절차를 별도로 설계해요.

## 3. 최소 데이터 모델

| 엔터티 | 주요 식별자·관계 | 범위 |
| --- | --- | --- |
| `users` | 내부 user ID, 인증 공급자 subject와 연결 | 전역 로그인. 다른 사업장 가입 현황은 고객에게 공개하지 않음 |
| `tenants` | UUID, 공개 slug, 표시명, 상태 | 계약 고객. slug는 변경 가능한 주소, 내부 참조는 UUID |
| `staff_memberships` | tenant ID + user ID, 조직 역할, 상태 | 직원 소속. 조직별로 독립 |
| `branches` | tenant ID + branch ID, slug, 시간대 | 조직 안의 지점 |
| `branch_assignments` | tenant ID + membership ID + branch ID, 지점 역할·행동 권한 | 지점 배정. 소속과 지점 모두 같은 tenant여야 함 |
| `customer_profiles` | tenant ID + customer ID, 고객 연락처·동의 연결 | 조직별 고객. 같은 사람도 다른 조직이면 별도 프로필 |
| `member_accounts` | tenant ID + user ID + customer ID | 인증된 회원과 해당 조직의 고객 연결 |
| `programs` | tenant ID + program ID | 브랜드 공통 프로그램. 업종 코드와 ID 분리 |
| `sessions` | tenant ID + branch ID + session ID + program ID | 회차. 해당 지점의 시간·정원·강사·공간 |
| `bookings` | tenant ID + branch ID + booking ID + session ID | 예약과 참여자. 고객·회차·지점 참조 일치 |
| `consent_events` | tenant ID + customer ID, 목적·시각·문서 버전 | 동의/철회 증적 |
| `proposals`·`executions` | tenant ID + branch ID, 제안/실행 ID·버전 | 승인과 실행 범위 |
| `jobs`·`audit_events` | tenant ID, 필요 시 branch ID, 실행 주체·대상 | 작업과 추적 |
| `subscriptions`·`usage_ledger` | tenant ID, 플랜 권한·청구 이벤트·사용량 | SaaS 구독·비용 |

테넌트 소유 업무 테이블의 `tenant_id`는 필수예요. 전역 로그인·공개 플랜 정의 등 예외 테이블은 명시적으로 제한해요. 지점 업무는 `branch_id`도 필수로 하고, 조직 전체 설정·프로그램에는 억지로 지점을 넣지 않아요.

`UNIQUE (tenant_id, id)`와 `(tenant_id, reference_id)` 복합 외래 키를 기본으로 고려해요. 예약이 가진 지점까지 회차와 일치해야 하면 `(tenant_id, branch_id, session_id)`로 참조해요. 서버가 실수해도 A의 예약에 B의 고객이나 회차를 연결할 수 없어야 해요.

업무 레코드의 `tenant_id` 변경은 일반 수정 API에서 허용하지 않아요. 사업장 이전·합병은 별도의 이관 작업이에요. 전화번호나 이름을 전역 고객 키로 사용하지 않고, 가족 공용 번호 같은 경우까지 고려해 연락처 일치만으로 계정을 자동 병합하지 않아요.

기본 색인은 실제 조회에 맞춰 `(tenant_id, branch_id, starts_at)`, `(tenant_id, customer_id, created_at)`, `(tenant_id, status, next_run_at)` 등을 검토해요. 예약 중복 방지 키도 조직 범위와 활성 상태를 반영해요.

## 4. 역할과 권한

| 주체 | 허용 범위 | 제한 |
| --- | --- | --- |
| 테넌트 최고관리자 | 자기 조직의 지점·직원·브랜드 정책 관리 | 다른 조직 접근 불가. 내보내기 등 민감 행위는 재인증 |
| 지점 오너 | 배정 지점 운영과 허용된 승인 | AI 권한은 브랜드 기본값보다 좁히기만 |
| 매니저 | 배정 지점 예약·고객·출석 등 허용 업무 | 조직 소유권·브랜드 기본 권한 변경 불가 |
| 직원 | 배정 지점의 명시된 실무 권한 | AI 승인·회원 신청 확정 권한은 별도 부여, 관리자 역할로 간주하지 않음 |
| 회원 | 가입한 조직에서 본인 예약·동의·문의 | 다른 회원·직원 메모 접근 불가 |
| 비회원 문의자 | 검증된 링크가 허용한 문의·행동 | 조직 고객 목록이나 다른 문의 접근 불가 |
| SaaS 지원 담당자 | 기본적으로 구독·서비스 상태 등 지원 메타데이터 | 고객 데이터 열람은 별도 사유·범위·만료·감사, 기본 전체 열람 금지 |

구독 결제·해지·조직 소유권 이전은 최고관리자라는 이유만으로 모두 허용하지 않고 계약 소유자 권한을 별도로 둬요. 한 지점의 ‘Team 화면 꺼짐’은 UI 설정이며 서버의 소속·권한 검사를 끄는 의미가 아니에요.

권한 판단은 ‘역할 이름’ 하나보다 **소속 활성 여부 + 조직 + 지점 배정 + 행동 권한 + 객체 소유 + 업무 상태**를 함께 사용해요. 예를 들어 `booking.confirm`, `attendance.write`, `ai_proposal.approve`, `customer.export`, `billing.manage`를 구분해요. 세부 권한표는 기존 D-01~D-15 결정과 맞춰 구현 전에 확정해요.

## 5. URL과 요청 처리

초기에는 경로 방식으로 시작하는 것을 제안해요. 아래 주소는 예시이며 실제 도메인은 미정이에요.

```text
app.example.com/t/jaejin/admin             조직 전체 관리
app.example.com/t/jaejin/b/gangnam/admin    지점 관리자
app.example.com/t/jaejin/b/gangnam/mobile   관리자 모바일
app.example.com/t/jaejin/member             브랜드 회원 앱
app.example.com/t/jaejin/b/gangnam/ask      비회원 공개 문의
```

회원은 브랜드 단위로 가입하고 회차의 지점으로 예약해요. 추후 `jaejin.example.com`이나 고객 소유 도메인을 추가해도 같은 내부 tenant UUID로 해석하도록 구성해요. 서브도메인은 식별 경로일 뿐 권한이나 DB 격리를 제공하지 않아요. 커스텀 도메인은 소유권 검증·인증서·예약된 이름·도메인 해제 후 탈취 방지까지 함께 설계해요.

요청 처리 순서는 다음과 같아요.

1. 검증된 서버 세션에서 사용자 ID를 얻어요.
2. URL의 tenant slug를 내부 ID로 해석하고, 활성 소속·테넌트 상태를 확인해요.
3. 지점과 대상 객체가 해당 테넌트에 속하는지, 필요한 행동 권한이 있는지 확인해요.
4. 검증된 `AccessContext`를 만들고 조직 범위가 필수인 repository/service에 전달해요.
5. 같은 DB 트랜잭션에서 RLS 컨텍스트를 설정하고 읽기·쓰기를 수행해요. 권한·버전·업무 상태를 다시 검증해야 하는 작업은 트랜잭션 안에서 처리해요.
6. 허용된 필드만 응답하고 감사·outbox를 기록해요.

공개 문의·공개 회차 목록은 직원 소속을 요구하는 흐름과 구분해요. 공개 가능한 조직/지점 정보만 별도 조회하고, 문의 내용은 링크/회원 인증 범위로 한정해요. 테넌트 생성·초대 수락도 일반 업무 요청과 별도의 제한된 초기화 서비스에서 처리해요.

**‘마지막으로 선택한 조직’ 쿠키를 유일한 처리 대상 기준으로 쓰지 않아요.** A 탭과 B 탭을 동시에 열어도 각 URL·action 대상과 검증된 소속을 기준으로 동작해야 해요. 변경 폼에는 대상 리소스와 예상 버전을 넣고, 권한·테넌트 불일치면 거절해요.

페이지·메뉴를 숨기는 것만으로 서버 변경 요청을 보호할 수 없어요. 모든 Server Action과 Route Handler의 진입점에서도 인증·객체 권한을 검사해요. [Next.js 인증 가이드](https://nextjs.org/docs/app/guides/authentication)

## 6. RLS와 연결 풀 적용 규칙

- 앱은 권한을 검증한 뒤 트랜잭션 범위의 조직/사용자 컨텍스트를 설정해요. raw `tenant_id` 헤더만 읽어서 DB 컨텍스트로 넣지 않아요.
- `USING`으로 조회/수정 대상, `WITH CHECK`로 새로 쓰는 행의 범위를 검사해요. 지점·본인 정보 등 더 좁은 권한은 서버 DAL에서 항상 검사하고, 필요한 테이블에는 DB 정책에도 반영해요.
- 컨텍스트가 없으면 업무 데이터를 반환하거나 쓰지 않는 기본 거부 정책을 사용해요.
- 연결 풀에서는 세션 전체에 남는 설정을 사용하지 않아요. 트랜잭션 내 `SET LOCAL`/동등한 로컬 설정과 질의가 같은 연결에서 실행되도록 DB 라이브러리·풀러를 확인해요. `SET LOCAL`은 트랜잭션 종료 시 끝나요. [PostgreSQL SET 문서](https://www.postgresql.org/docs/current/sql-set.html)
- RLS 정책의 소속 조회가 자기 정책을 다시 호출하는 재귀를 만들지 않도록 인증/소속 테이블 접근을 별도로 설계하고 테스트해요.
- 전역 DB 권한이 필요한 마이그레이션·백업과 고객 요청 처리를 같은 계정으로 실행하지 않아요. 운영 워커에도 불필요한 전체 조직 우회 권한을 주지 않아요.
- 서버 설정 방식의 조직 컨텍스트는 서버가 신뢰 경계예요. RLS를 임의 SQL 실행이나 서버 침해까지 해결하는 장치로 설명하지 않아요. 매개변수 질의·최소 권한·비밀 관리도 필요해요.

초기 RLS는 `db/migrations/0001_tenant_foundation.sql`에 구현했고 PostgreSQL 17 통합 테스트 16개를 통과했어요. Supabase 서울의 제한된 계정·transaction pooler에서도 격리·감사·권한 회수를 검증했으며 예약·파일·AI·큐는 아직 미구현이에요.

## 7. DB 밖의 격리

| 대상 | 적용 규칙 |
| --- | --- |
| 캐시 | tenant·branch·조회 조건·필요한 사용자/권한 범위를 키에 반영. 개인정보 응답 공개 캐시 금지 |
| 파일 | tenant별 객체 경로 + 서버 권한 검사. 경로가 분리됐다고 공개 버킷으로 만들지 않음 |
| AI 검색 | tenant 필터를 서버에서 강제. 클라이언트/모델이 필터를 제거할 수 없게 함. 타 조직 정보는 프롬프트에 넣기 전에 제외 |
| 작업 큐 | tenant·branch·작업 ID·정책/대상 버전을 저장. 실행 시 테넌트 상태와 승인/권한·동의를 재검사 |
| 웹훅 | 공급자 서명 확인 후 저장된 연결 계정에서 tenant 매핑. payload의 tenant 주장만 신뢰하지 않음 |
| 감사·지원 | 행위자·tenant·branch·대상·결과를 추적. 지원 담당자의 조회 자체도 감사 |
| 사용량 | AI·메시지·저장량을 tenant별 집계. 중복 이벤트 과금 방지와 조직별 한도 |
| 이벤트/실시간 구독 | 구독 시 조직·지점·본인 범위 검증. 채널 이름만 안다고 구독 불가, 권한 회수 시 종료 |
| 삭제·복구 | tenant의 DB·파일·검색 색인·작업·연동 토큰을 함께 처리. 다른 tenant 영향 없이 검증 |

## 8. 현재 코드에서 달라질 부분

| 현재 | 변경 방향 |
| --- | --- |
| `src/data/`의 재진필라테스 샘플 | 데모 fixture로 이동. 운영 화면은 서버가 허용한 DTO만 받음 |
| 고정 브랜드·홍지수·강남점 셸 | 검증된 조직·지점 컨텍스트에서 표시. 전환 시 권한 재검사 |
| `/admin`, `/mobile`, `/member`, `/ask` | 운영 경로에 조직 식별 추가. 기존 공개 데모는 별도 환경에 유지 |
| `?as=admin`, 프로토타입 역할 전환 | 운영에서 제거. 서버 소속·행동 권한으로 대체 |
| 컴포넌트별 예약·출석 `useState` 저장 | 공통 업무 서비스·DB 트랜잭션·서버 결과 갱신 |
| 회원 이름·강사 이름으로 연결 | 조직 범위의 불변 ID와 복합 참조 |
| AI 권한·초안·통계 샘플 | 조직별 정책·자료·실행 결과. 브랜드 정책을 지점에서 확대할 수 없게 검사 |

첫 적용에서 47개 화면을 한꺼번에 재작성하지 않아요. 인증·DB 경계를 만든 다음 회차·예약 한 흐름을 운영 어댑터로 옮기고, 동일 패턴을 나머지 화면에 확장해요.

## 9. 첫 구현 묶음과 인수 조건

1. **DB·인증 어댑터 결정(공급자 선정·개발 DB 연결 완료)**: Supabase PostgreSQL + Auth를 첫 대상으로 선정했어요([선정 근거](PROVIDER_DECISION.md)). 서울 개발 DB 연결·원격 격리 검증·인증 어댑터 구현과 실제 계정의 기본 흐름 검증을 완료했어요. PostgreSQL 공급자/지역/백업, 인증 공급자, DB 접근 라이브러리, 개발·스테이징 환경을 정해요. 멀티테넌트 결정만으로 특정 서비스 구매·프로비저닝을 확정하지 않아요.
2. **최소 스키마와 격리(초기 기반 완료)**: tenants, users 연결, staff_memberships, branches, branch_assignments와 두 조직 fixture. RLS·복합 참조·최소 DB 계정 권한부터 테스트해요.
3. **온보딩과 소속**: 조직·첫 지점 생성, 본인 소유권 부여, 직원 초대/수락/회수, 조직·지점 선택. 생성 재요청이 조직을 중복으로 만들지 않게 해요.
4. **수동 예약 한 흐름**: 회차 생성 → 회원 신청 → 관리자 확정 → 출석 조회. PC·모바일·회원이 같은 데이터 조회, 정원 경쟁·중복 요청 방지.
5. **구독·운영·확장**: tenant별 기능 권한·사용량·감사·백업 복구·메시지 작업을 붙이고 AI 기능을 단계적으로 연결해요.

출시 전 반드시 확인할 격리 테스트는 다음과 같아요.

- A의 직원이 B의 ID를 URL·본문·검색 조건·파일 경로에 넣어도 B의 정보를 읽거나 변경하지 못해요.
- A의 예약에 B의 고객/회차를 넣으면 DB 참조 제약에서도 거절돼요.
- A의 두 지점 중 하나만 배정된 직원은 다른 지점의 예약·메모를 볼 수 없어요.
- 동일 로그인 계정으로 A/B 탭을 번갈아 사용해도 예약·폼·캐시·알림이 섞이지 않아요.
- 연결 풀의 같은 연결이 A 요청 다음 B 요청에 재사용돼도 조직 컨텍스트가 남지 않아요. 컨텍스트 없는 요청은 거부돼요.
- 같은 이름·전화번호의 고객이 A와 B에 존재해도 각 기록·동의·AI 근거는 분리돼요.
- 직원 권한 회수·조직 정지 후 다음 요청·대기 작업·실시간 구독이 정의한 정책대로 제한돼요.
- 파일·AI 검색·내보내기·작업 재시도에서도 동일한 격리가 유지돼요.
- 조직별 동시 작업 한도로 한 고객의 폭주가 다른 고객의 예약 처리를 독점하지 않아요.
- 테넌트 종료·선택 복구 연습에서 다른 테넌트 데이터가 변경되지 않아요.

이 테스트는 실제 PostgreSQL의 앱 실행 역할로 수행해요. 모든 테스트를 RLS 우회 관리자 계정이나 mock DB로만 실행하면 격리 검증이 되지 않아요.
