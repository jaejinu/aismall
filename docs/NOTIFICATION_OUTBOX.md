# 예약 알림 대기열 기반

2026-10-16. [README](../README.md) · [아키텍처](ARCHITECTURE.md)

## 구현 범위

예약 확정·회차 변경·취소와 알림 요청을 같은 트랜잭션에 저장해요. 관리자·회원·자동 확정 모두 예약 테이블 트리거를 거쳐요. 출석 상태만 바뀌면 생성하지 않으며, 과거 이벤트를 소급 생성하지 않아요. 예약·감사·대기열 중 하나라도 실패하면 전체 롤백돼요.

이메일 수신 동의·대상 조회·발송 유효성 검사 기반을 구현했어요. Supabase 현재 이메일 조회와 선택형 Resend adapter 코드는 구현했지만 실제 키·발신자·워커 로그인·스케줄은 미연결이에요. 관리자는 예약 관리의 알림 현황 탭에서 대기열을 조회할 수 있어요. 화면의 ‘알림은 자동 발송되지 않아요’ 안내는 그대로 맞아요.

| 위치 | 역할 |
| --- | --- |
| db/migrations/0012_booking_outbox.sql | 비공개 큐·트리거·점유/완료 함수·전용 권한 |
| src/server/notifications/outbox.ts | 별도 워커 DB 풀 검사·작업 조회/결과 저장 |
| tests/notification-outbox.test.ts | 원자성·격리·경합·순서·재시도·만료 복구 |
| scripts/verify-hosted-outbox.mjs | 유휴 개발 큐에서 합성 검증 후 전체 롤백 |

유일 키는 조직·지점·예약 ID·예약 버전이에요. 같은 예약 요청 재시도는 중복 이벤트를 만들지 않아요. payload에는 스키마 버전·고객/회차/프로그램 ID·당시 일정·이전 회차 ID만 저장해요. 이름·연락처·변경 사유·비밀 키는 복제하지 않아요. ID와 일정도 개인정보 보관/삭제 정책에 포함해야 해요.

## 처리 규칙

- pending → processing → delivered 또는 재시도 pending / 최종 실패 dead.
- 1~50건을 FOR UPDATE SKIP LOCKED로 점유해 여러 워커가 같은 작업을 동시에 처리하지 않아요.
- 점유는 60초, 매번 새 lease token을 발급해요. 만료·다른 토큰·완료된 작업의 결과 저장은 거절해요.
- 일시 실패는 30·60·120·240초 후 재시도해요. 최대 5번 시도하며 마지막 실패·영구 실패·5번째 점유 만료는 dead로 남겨요.
- 같은 예약의 낮은 버전이 대기/처리 중이면 뒤 이벤트는 기다려요. 앞 이벤트가 완료/최종 실패가 되면 다음 이벤트를 처리해요.
- 정지 조직·닫힌 지점은 새 작업을 점유하지 않아요. 점유 이후 상태가 바뀔 수 있으므로 0015의 최종 판정 함수로 발송 직전 권한·연결을 재검사해요. 외부 전송 직후의 회수까지 원자적으로 보장하지는 못해요.
- 오류 원문 대신 temporary / permanent / lease_expired만 저장해요.

외부 전송과 DB 완료 저장은 한 트랜잭션이 아니에요. 전송 후 워커가 중단되면 재실행될 수 있어 **공급자 중복 방지 키에 outbox ID를 사용해야 해요**. 현재 기반은 재시도 가능한 처리이며 정확히 한 번 발송을 보장하지 않아요. 공급자의 키 지원과 유효 기간을 확인한 뒤 연결해야 해요.

## 권한·남은 작업

웹 runtime은 대기열 테이블 직접 조회/수정·워커 점유·완료를 할 수 없어요. 제한된 현황 조회와 재처리 함수만 실행해요. aismall_notification_worker는 NOLOGIN이며 점유·완료·발송 준비·점유 대상 인증 ID 조회·결과 기록 함수만 실행하고 고객·예약 테이블은 직접 읽지 못해요. 여러 조직의 작업을 처리하는 시스템 권한이므로 사용자 요청용 계정에 부여하지 않아요.

워커 로그인·비밀번호·환경 변수·스케줄은 생성하지 않았어요. helper는 superuser/BYPASSRLS·웹 runtime·워커 역할 미보유 연결을 거절해요. 마이그레이션 계정은 실제 워커로 사용하지 않아요.

다음은 인증/발송 공급자 adapter·타임아웃·중복 방지, 지점 채널 관리, 차단 결과 기록·처리 정책, 모니터링·보관 기간이에요. 실제 주소로 보내기 전에 테스트 대상과 운영 발송 범위를 정해야 해요.

## 검증

타입·린트·Webpack 빌드 및 **125개 테스트(설정/CLI 17 + DB/서명 108)** 통과. 로컬에서는 실제 제한된 워커 역할로 접근 차단·동시 점유·순서·오래된 토큰·지수 대기·5회 한도·조직/지점 차단을 확인했어요.

서울 개발 DB에 0012 적용 완료. node scripts/verify-hosted-outbox.mjs PROJECT_REF는 먼저 유휴 큐인지 검사하고 합성 예약→재시도→취소→큐 생성→점유→실패 재시도를 확인한 뒤 롤백해요. 호스팅 역할 전환 제한으로 원격은 마이그레이션 계정의 기능 검증과 has_function_privilege 권한 조회를 구분했어요. 실제 워커 로그인 원격 접속 검증은 남아 있어요.

실제 메시지 발송·운영 배포·커밋은 없어요. 기존 개발 고객·예약 데이터도 변경하지 않았어요.

## 지점별 알림 현황 (2026-10-16)

0013은 private 대기열에서 필요한 필드만 반환하는 제한된 조회 함수를 추가해요. 최고관리자·배정된 사업장 오너/매니저만 접근하며, 일반 직원·회원·다른 조직/지점·닫힌 지점은 차단해요. 웹 runtime의 테이블 직접 조회와 워커 점유 권한은 계속 없어요.

예약 관리의 **알림 현황** 탭에서 지점 전체 상태별 건수, 응답 기한 경과 건수, 상태 필터, 생성 순 50건 페이지 이동, 새로고침을 제공해요. 개별 항목에는 고객·프로그램·이벤트 당시 일정·시도 횟수·오류 분류·다음 처리 가능 시각·종료 시각·예약/요청 ID가 표시돼요. 처리 토큰·원본 payload·수신 주소는 반환하지 않아요.

조회 오류가 나면 기존 목록·집계도 지워 권한 회수 후 이전 정보가 남지 않게 해요. 페이지 이동 중 새로운 이벤트가 추가되면 위치가 바뀔 수 있어요. 과거 예약 이벤트를 소급 만들지 않아 기존 지점은 처음에는 빈 목록일 수 있어요. 실제 발송 미연결 안내를 표시해요.

로컬 권한·토큰 비노출·53건 페이지 검증과 서울 원격 집계·필터·오류 조회 롤백을 통과했어요. 실제 컴포넌트/프로덕션 CSS를 사용한 합성 화면에서 390px 실패 필터·빈 상태·조회 오류 시 정보 제거를 확인했어요. 실제 관리자 로그인 화면의 통합 검증과 Figma 파일 반영은 별도로 남아 있어요.

## 최종 실패 수동 재처리 (0014)

알림 현황에서 조건을 만족하는 최종 실패에 ‘다시 처리 요청’을 제공해요. 기존 지점 관리 권한을 매번 재검사하고, 동일 요청 ID를 유지해 공급자의 중복 방지 키가 바뀌지 않아요.

- 최초 생성 후 24시간 이내, 일정 시작 전, 현재 예약 버전과 일치하는 실패만 허용해요. 출석 정정 등으로 버전이 바뀐 경우에도 보수적으로 차단해요.
- 수동 재처리는 최대 3회이며 매번 시도 횟수를 0으로 초기화해 자동 시도 최대 5회를 다시 허용해요. 원래 생성 시각은 유지해요.
- 화면이 읽은 재처리 세대를 서버에 전달해요. 같은 세대의 동시/반복 요청은 한 번만 반영하고, 이미 진행된 점유·후속 실패를 초기화하지 않아요. 더 오래된 세대는 거절해요.
- 예약 → 대기열 순으로 잠가 예약 변경과 직렬화해요. 감사 기록에 작업 ID·세대·실행자·직전 시도 수·오류 분류·시각을 보관하고, 기록 실패 시 상태 변경도 롤백해요. 감사 테이블은 웹/워커 직접 접근 불가예요.

이 시간·버전 제한은 **수동 재처리 정책**이에요. 기존 pending 작업의 실제 발송 유효성, 수신 대상·연결 회수·동의·채널 설정·공급자 중복 방지 유효 기간은 발송 연결 전에 별도로 구현해야 해요. 현재는 공급자·워커 미연결로 재처리 버튼도 대기열 상태만 변경해요.

91개 테스트(설정 7 + DB 84), 타입·린트·Webpack 빌드 통과. 서울 개발 DB 0014 적용 후 합성 최종 실패→재처리→동일 요청 재실행→감사 1건 검증을 전체 롤백했어요. 실제 컴포넌트/프로덕션 CSS의 390px 합성 화면에서 버튼·대기 전환·실패 목록 제거를 확인했어요. 실제 관리자 로그인 통합 검증·Figma 반영은 남아 있어요.

## 이메일 수신 선택과 발송 판정 (0015)

회원 **내 정보 → 연결된 사업장 → 예약 이메일 알림**에서 사업장별 수신 여부를 저장해요. 기본값은 받지 않기이며 광고 동의와 섞지 않아요. 활성 회원 연결의 소유자만 변경하고, 수신을 켤 때는 서버가 확인한 현재 인증 이메일과 연결 이메일이 같아야 해요. 이메일이 바뀌어도 수신 끄기는 허용해요. 설정에 버전을 적용해 오래된 화면의 저장이 최신 선택을 덮어쓰지 않게 하고, 상태 전환·실행자·정책 버전 `booking-email-v1`을 원자적으로 기록해요. 연락처를 동의 테이블이나 감사 기록에 복제하지 않아요.

동의 이후 생성된 이벤트만 대상이에요. 껐다가 다시 켜면 새 동의 시각 이전 이벤트는 제외해요. 수신 미동의가 예약 이용을 막지는 않아요. 지점 이메일 채널은 행이 없거나 false이면 차단하며 기존 지점에 활성 값을 넣지 않았어요. 현재 채널 관리 UI/API도 없어 운영자가 임의로 실제 발송을 시작할 수 없어요.

워커 전용 `prepareBookingNotification`은 유효한 작업 ID·점유 토큰을 요구하고 다음을 검사해요.

| 검사 | 차단 코드 |
| --- | --- |
| 조직·지점 비활성 | inactive_scope |
| 예약 버전 변경 | superseded |
| 최초 생성 24시간 경과 또는 일정 시작 | expired_event |
| 활성 회원 연결 없음·회수·사용자 정지 | recipient_unavailable |
| 수신 미동의·철회 | consent_missing |
| 현재 동의보다 이전 이벤트 | before_consent |
| 지점 이메일 채널 꺼짐 | channel_disabled |

차단 응답에는 주소가 없어요. 허용 응답에만 연결 이메일·내부 사용자 ID·점유 기한·원래 outbox ID 중복 방지 키를 반환해요. 주소를 outbox나 관리자 현황에 넣지 않으며 워커도 관련 테이블 직접 조회 권한이 없어요.

실제 전송 구현은 상위 함수 **authorizeBookingDelivery**를 호출해야 해요. 이 함수는 신뢰할 수 있는 인증 공급자 조회 콜백으로 현재 인증 이메일을 다시 확인해요. 미인증·주소 변경·조회 실패는 `identity_unverified`로 차단하며, 조회 뒤 DB 조건과 점유 기한을 재검사해요. 콜백에 클라이언트 입력이나 캐시된 이메일을 넘기면 안 돼요. Supabase 인증 조회 adapter와 발송 adapter 연결은 다음 작업이며 현재 자동 실행 경로는 없어요.

이 판정은 읽기 전용이며 성공을 영구 발송 허가로 저장하거나 재사용하면 안 돼요. DB 검사와 외부 전송 사이의 동시 변경까지 원자적으로 막지는 못해요. 차단을 ‘발송 완료’로 기록하지 않으며, 차단 사유를 별도 보관하고 건너뛰는 워커 실행 정책은 남아 있어요. 기존 low-level 완료 함수는 전송 증거를 확인하지 않으므로 새 전송 경로는 최종 판정과 공급자 응답 검사를 반드시 거쳐야 해요.

총 97개 테스트(설정 7 + DB 90): 소유권·인증 이메일·중복/낡은 저장·감사 롤백·주소 비노출·동의 전 이벤트·회수·비활성·시간/버전·토큰·인증 조회 실패 및 조회 중 채널 회수를 검증했어요. 서울 0015 적용 및 합성 동의/철회/발송 판정 전체 롤백을 완료했어요. 실제 회원 컴포넌트와 프로덕션 CSS로 390px 기본값·동의 안내·합성 저장 피드백을 확인했어요. 현재 로그인 계정에 활성 회원 연결이 없어 실제 회원 저장 E2E는 하지 않았어요. 실제 계정 동의·채널 상태를 변경하거나 이메일을 보내지 않았어요.

## 제한된 워커 실행과 공급자 adapter (0016)

`runNotificationBatch`는 기본 비활성이에요. `enabled: true`를 명시한 호출만 최대 1~50건을 순차 처리해요. 매번 1건만 점유하여 뒤 작업의 점유 시간이 대기 중 소진되는 일을 피하고, 최종 발송 판정 → 전송 → 결과 기록 순으로 실행해요. 웹 요청/cron과 연결하지 않았어요.

- `supabaseRecipientVerifier`: 해당 점유 작업의 수신자에 한해서 내부 사용자 ID를 인증 issuer/subject로 변환해요. 임의 사용자 전체 조회는 제공하지 않아요. issuer 일치·UUID·현재 인증 이메일·삭제/정지 여부를 검사하고, 조회 실패는 일시 장애로 처리해요. 5초 timeout, redirect 거절, no-store를 적용해요. 새 secret 키는 apikey 헤더로만 전송하며 웹 runtime 설정에서 읽지 않아요.
- `resendTransport`: 공급자 교체가 가능한 `EmailTransport` 구현이에요. 계정을 만들거나 실제 공급자 사용을 확정한 것은 아니에요. 명시적 키·발신 이메일과 비어 있지 않은 수신자 허용 목록이 필요해요. 허용 목록 밖 주소는 네트워크 호출 전에 거절해요. 원래 outbox ID를 Idempotency-Key로 사용하고 8초 timeout, redirect 거절을 적용해요. 408/429/5xx/네트워크 실패/불완전 성공 응답은 재시도, 나머지 HTTP 오류는 최종 실패로 분류해요. 다른 payload의 409 충돌은 자동으로 새 키를 만들지 않아요.
- 텍스트 본문은 예약 이벤트와 한국 시간 일정에서 결정적으로 생성해요. 고객명·연락처·변경 사유·조직/고객 내부 ID는 본문에 포함하지 않아요. 같은 이벤트 재시도 시 본문과 중복 방지 키를 유지해요. 발신 주소·템플릿 변경도 기존 키와 충돌할 수 있으므로 처리 중인 이벤트의 설정은 고정해야 해요.

`record_notification_result`는 점유 토큰을 재검사하고 상태 변경과 private 결과 이력을 같은 트랜잭션에 저장해요. 기록 실패 시 완료 저장도 롤백돼요. 결과에는 outbox ID·수동 재처리 세대·자동 시도 번호·분류 코드·시각만 저장하며 이메일·토큰·공급자 오류 원문을 남기지 않아요.

| 결과 | 처리 |
| --- | --- |
| provider_accepted | 기존 delivered 상태로 완료 |
| transport_temporary / identity_unavailable / channel_disabled | 기존 backoff, 5회 소진 시 dead |
| transport_permanent / identity_unverified / 기타 정책 차단 | dead, 완료로 기록하지 않음 |

`delivered`는 현재 공급자 접수 성공을 뜻해요. 실제 수신함 도착·반송·스팸 분류까지 확인한 상태가 아니며 webhook 수신 상태 모델은 남아 있어요. 완료 DB 저장이 실패하면 같은 실행에서 다시 전송하지 않고 lease 복구에 맡겨요. 공급자 성공 뒤 DB 장애가 발생할 수 있으므로 정확히 한 번 전송 보장은 여전히 없어요. 최종 판정부터 외부 API 사이의 동시 변경도 원자적으로 묶을 수 없어요.

### 사용 경계

`worker.ts`의 실행 함수에 별도 워커 Pool, `supabaseRecipientVerifier(pool, config)`, `resendTransport(config)`를 명시적으로 주입해요. 웹 runtime Pool이나 migration owner는 거절돼요. secret·발신 도메인·전용 워커 계정·허용 수신자·채널 활성화·스케줄은 이번에 생성/변경하지 않았어요. 따라서 실제 발송은 없어요. 실운영 전에는 설정 검증 도구, 결과 사유의 관리자 표시, 전송 허가와 수신자 범위 확정, 공급자 webhook, 보관/삭제 정책을 마무리해야 해요.

## 관리자 처리 사유와 파일럿 점검 (0017)

알림 현황은 가장 최근 처리 결과의 사유·시각·자동 시도 횟수·수동 재처리 회차를 표시해요. 최신 결과는 회차/시도 번호 기준으로 선택해요. 수동 재처리 직후 아직 새 결과가 없으면 이전 회차 기록임을 표시해 현재 결과로 오해하지 않게 해요. 공급자 접수 성공은 수신함 도착 보장이 아님을 안내해요. 이메일·인증 ID·토큰·공급자 오류 원문은 반환하지 않아요. 결과 이력이 없는 기존 항목은 기존 오류 분류를 표시해요.

### 파일럿 설정 점검 명령

```sh
npm run notifications:check
npm run notifications:check -- --database-readonly
```

기본 명령은 환경 변수 형식만 검사하고 네트워크에 접속하지 않아요. 선택 옵션은 명시한 워커 DB에만 `BEGIN READ ONLY`로 접속하여 역할·필수 함수 권한·업무/비공개 테이블 직접 권한 부재를 검사한 뒤 롤백해요. 대기열 점유, 인증 사용자 조회, 이메일 전송은 하지 않아요. DB 점검 성공도 API 키 유효성·발신 도메인 인증·실제 수신 성공을 뜻하지 않아요.

별도 `.env.worker.local` 또는 명령 실행 환경에서 다음 값을 읽어요. 웹용 `.env.local`은 자동으로 읽지 않아요. `.env.worker.local`은 기존 `.env*` 규칙으로 git에서 제외돼요. 이번 작업에서는 파일/키/로그인을 생성하지 않았어요.

| 변수 | 조건 |
| --- | --- |
| SUPABASE_URL | 개발 프로젝트 HTTPS URL |
| WORKER_DATABASE_URL | 동일 프로젝트 `aismall_delivery` 로그인, sslmode=verify-full; 직접 연결 또는 풀러 |
| WORKER_SUPABASE_SECRET_KEY | 워커 전용 서버 secret 키, 웹용 publishable 키 불가 |
| RESEND_API_KEY | 전송용 API 키 |
| NOTIFICATION_FROM | 발신 이메일 (실제 도메인 검증은 별도) |
| NOTIFICATION_ALLOWED_RECIPIENTS | 쉼표로 구분한 중복 없는 파일럿 이메일 1~20개 |
| NOTIFICATION_WORKER_ENABLED | 점검 단계에서는 반드시 false |

검사 결과는 변수 이름과 일반 오류만 출력하고 URL·비밀번호·키·이메일 값·드라이버 오류 원문은 숨겨요. `aismall_delivery`는 앞으로 준비할 전용 로그인 이름이며, 최소 권한 `aismall_notification_worker`만 상속해야 해요. 운영용 로그인/시크릿 관리는 별도 배포 단계에 속해요.

현재 환경의 기본 점검 결과는 **필수 워커 설정 누락**이에요. 따라서 실제 DB 워커 로그인 원격 점검과 공급자 인증·도메인 검증은 아직 수행하지 않았어요. 준비된 것으로 표시하거나 자동으로 발송을 켜지 않았어요.

110개 테스트(설정 11 + DB 99), 타입·린트·Webpack 빌드 통과. 0017 서울 적용 및 원격 결과 projection/토큰 비노출 롤백 검증 완료. 390px 합성 화면에서 차단 사유·이전 처리 회차 구분을 확인했어요. Figma 원본 동기화는 별도로 남아 있어요.

## 파일럿 실행 범위와 미리보기 (0018)

`runNotificationBatch(pool,{scope:{tenantId,branchId},...})`는 조직·지점을 반드시 지정해야 해요. 기본 비활성·건별 점유·최대 50건·동의/인증/허용 수신자 검사는 유지해요. 새 SQL `claim_scoped_booking_notifications`는 점유뿐 아니라 5회 소진된 만료 lease 정리도 같은 지점 안에서만 수행해요. 존재하지 않거나 조직과 맞지 않는 지점은 거절해요.

별도 `.env.worker.local`에 `NOTIFICATION_TENANT_ID`와 `NOTIFICATION_BRANCH_ID`를 UUID로 지정한 후:

```sh
npm run notifications:check -- --scope-preview
```

설정과 최소 권한을 확인한 뒤 `BEGIN READ ONLY`에서 대상 UUID·활성 상태·이메일 채널 상태·대기/처리 중/만료 lease 건수만 반환해요. 고객 주소·본문·작업 토큰은 반환하지 않아요. 대기 건수는 발송 가능 건수가 아니며, 미리보기 이후 상태는 바뀔 수 있어요. 채널과 수신 동의는 자동 활성화하지 않아요.

기존 전역 claim 함수는 저수준 검증/운영 호환용으로 남아 있고 공통 워커 역할이 실행할 수 있어요. 따라서 scope는 파일럿 오작동 방지이며 탈취된 워커 자격 증명을 특정 조직으로 격리하는 보안 경계는 아니에요. 웹 runtime에는 두 새 함수 모두 권한이 없어요.

111개 테스트(설정 11 + DB 100), 타입·린트·Webpack 빌드 통과. 다른 조직/같은 조직의 다른 지점의 소진된 lease 불변, 읽기 전용 조회 전후 전체 행 불변, 동시 중복 점유 방지와 잘못된 scope/웹 역할 거절을 확인했어요. 서울 0018 적용과 합성 데이터 롤백 검증 완료. 실제 전용 로그인/공급자 설정은 준비되지 않았으며 실행 CLI 연결·실발송·스케줄·webhook 처리는 남아 있어요.

## 파일럿 실행 명령

`npm run notifications:pilot`은 기본적으로 읽기 전용 DB 권한/범위 미리보기를 실행해요. `.env.worker.local`만 읽으며 웹의 `.env.local`을 자동 사용하지 않아요. 0018까지 적용된 DB와 위에 설명한 전용 워커 설정, 조직·지점 UUID가 필요해요. 미리보기에서는 `NOTIFICATION_WORKER_ENABLED=false`여야 해요. 공급자 adapter는 로드하지 않아요.

실제 발송 준비가 끝난 환경에서만 `NOTIFICATION_WORKER_ENABLED=true`와 다음 명령을 함께 사용해요:

```sh
npm run notifications:pilot -- --execute --limit 1
```

`--execute`나 활성화 설정 중 하나만 있으면 실행을 거절해요. 기본 한도는 1건, 허용 범위는 1~50건이며 반복 스케줄은 없어요. 잘못된 옵션/중복 옵션·scope·허용 수신자 목록·DB 계정을 연결 전에 검사하고, DB 최소 권한과 조직/지점/채널 활성 상태를 확인한 뒤 기존 워커를 호출해요. 채널 활성화나 회원 동의를 자동 변경하지 않아요. 실제 실행 후에는 활성화 설정을 다시 false로 돌려 미리보기 모드로 운영해요.

결과 JSON의 `claimed`는 점유, `accepted`는 공급자 접수(실제 전달 아님), `blocked`는 최종 차단, `retrying`은 재시도 대기, `failed`는 판정/결과 저장 실패 건수예요. 개인정보·비밀 키·공급자 응답은 출력하지 않아요. 종료 코드는 정상 0, 설정/DB/실행 오류 1, 처리 결과에 차단/재시도/실패가 있으면 2예요. 실행 도중 오류가 나면 일부 발송은 이미 접수됐을 수 있어요. 자동 재실행하지 말고 관리자 알림 현황을 확인해요. DB 결과 저장에 실패한 건은 기존 lease 만료와 동일 idempotency key로 복구해요.

검증: 설정/CLI 17개와 DB 100개, 타입·린트·Webpack 빌드. 실제 공급자 전송은 합성 HTTP 테스트로만 검증했으며 전용 로그인/키/발신자/채널 활성화와 실제 전달 검증은 남아 있어요. 이 작업에는 DB 스키마 변경이 없어요. 다음은 공급자 전달/반송 webhook 모델과 수신 처리예요.

## 전달·반송 webhook (0019)

`POST /api/webhooks/resend`는 Node.js Route Handler예요. 기본 비활성이며 활성화 전까지 503을 반환해요. 로그인 쿠키 대신 Svix 서명·타임스탬프를 검사해요. 64 KiB 제한을 스트림에 적용하고, 원문을 검증한 뒤 JSON을 파싱해요. 변조/잘못된 본문은 400, 크기 초과는 413, 저장 실패는 503, 성공/서명 검증된 미지원 이벤트는 204예요. 응답·로그에는 본문이나 원시 DB 오류를 넣지 않아요.

별도 준비할 서버 환경:

| 변수 | 의미 |
| --- | --- |
| `NOTIFICATION_WEBHOOK_ENABLED` | 명시적 `true`일 때만 수신 활성화 |
| `RESEND_WEBHOOK_SECRET` | 해당 endpoint의 Svix 서명 키 |
| `NOTIFICATION_WEBHOOK_DATABASE_URL` | `verify-full` TLS, 별도 webhook 로그인 연결 |

`aismall_notification_webhook`은 NOLOGIN 권한 역할만 생성했어요. 실제 로그인/비밀번호는 만들지 않았어요. 그 역할만 상속하는 전용 로그인을 준비해야 하며 app·발송 worker·superuser·BYPASSRLS·CREATEDB·CREATEROLE 계정은 수신 코드에서 거절해요. 이 역할에는 제한된 이벤트 저장 함수만 허용하고 직접 테이블 접근·알림 점유는 허용하지 않아요. 웹 runtime 권한을 늘리지 않아요.

Resend adapter는 공급자 이메일 ID를 반환하며, 워커는 접수 결과·receipt 매핑을 원자적으로 저장해요. 이미 사용된 공급자 ID를 다른 작업에 연결하거나 만료된 lease로 저장하면 전체 롤백해요. 기존 모의/공급자 중립 `accepted` 결과에는 receipt가 없을 수 있어요.

저장 이벤트는 `email.sent`, `email.delivered`, `email.delivery_delayed`, `email.bounced`, `email.complained`, `email.failed`, `email.suppressed`예요. Svix 이벤트 ID로 중복을 제거하며 같은 ID에 다른 값이 오면 거절해요. 주소·제목·본문·반송 원문은 저장하지 않아요. 응답보다 먼저 도착한 webhook도 이메일 ID로 추후 receipt와 연결돼요. 순서에 따라 단일 상태를 덮어쓰지 않고 관측 사실을 보존해요. 지점 권한을 검사하는 `notification_delivery_status`는 유형별 최초 시각만 반환하며 공급자 ID는 노출하지 않아요. 전달은 수신 메일 서버의 접수이며 열람/받은편지함 도착 보장은 아니에요.

알림 큐의 기존 `delivered`는 공급자 접수 완료 의미를 유지해요. webhook이 큐를 재시도하거나 회원 동의를 바꾸지 않아요. 관리자 UI 전달 결과 표시는 다음 작업이고, 현재는 지점 권한 조회 함수까지 구현했어요. 반송/신고 후 향후 발송 억제 정책, 미연결 이벤트 보관 기간·정리 작업, 운영 rate limit·알림, 실제 공급자 endpoint 등록/키 설정/재전송 E2E는 남아 있어요. 전용 발송용 Resend 프로젝트/endpoint 사용이 전제예요.

검증: 125개 테스트(설정/CLI 17 + DB/서명 108), 타입·린트·Webpack 빌드. 서명 변조·오래된/미래 타임스탬프·본문 크기 제한·중복/역순/선도착·원자성·권한 격리 확인. 서울 0019 적용 및 합성 원격 롤백 완료. 실제 발송/공급자 등록/수신 활성화/공개 배포 없음.

참고: [Resend 서명 검증](https://resend.com/docs/webhooks/verify-webhooks-requests), [이벤트 정의](https://resend.com/docs/webhooks/event-types). 설치된 Svix의 `verify`는 검증만 수행하므로 검증 후 별도 JSON 파싱해요. 의존성 audit의 high 5건은 기존 eslint-config-next → fast-glob → micromatch → braces 체인이고 새 Svix 체인은 아니에요. 자동 제안이 Next ESLint 14로의 주요 버전 변경이라 강제 적용하지 않았으며 별도 정리가 남아 있어요.
