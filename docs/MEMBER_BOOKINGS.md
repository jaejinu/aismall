# 회원 예약 신청·확정·변경·취소

[README](../README.md) · [수동 예약](MANUAL_BOOKINGS.md) · [아키텍처](ARCHITECTURE.md)

## 구현 범위

`/workspace/member`에서 로그인한 회원이 자기 지점의 회차를 신청하고 신청·예약을 확인해요. 지점 예약 화면의 **회원 신청·승인 대기**에서 운영자가 승인하거나 거절해요. AI 승인함과 분리해요. 기존 `/member/*`는 샘플 데모예요.

관리자 확인형과 프로그램별 자동 확정을 지원해요. 대기열·참석 확인 응답·알림은 후속 범위예요. 모든 프로그램의 회원 신청은 기본으로 닫혀 있어요.

## 사용 순서

1. 관리자가 기존 고객을 선택하고 회원이 사용할 로그인 이메일로 일회용 연결 코드를 만들어요. 코드는 화면에 한 번 표시하며 이메일은 자동 발송하지 않아요.
2. 회원이 해당 이메일의 확인된 계정으로 로그인해 `/workspace/member`에서 코드를 수락해요. 코드 유효 기간은 7일이며 재발급하면 이전 코드가 무효가 돼요.
3. 관리자가 프로그램의 회원 신청을 열고 확정 방식(관리자 확인/자동)을 선택해요. 마감은 시작 24시간 전 또는 2시간 전으로 정해요.
4. 회원이 회차를 신청해요. **관리자 확인형 신청은 자리를 확보하지 않아요.** 대기 중에는 직접 철회할 수 있어요. 자동 확정은 즉시 예약과 자리를 확보해요.
5. 관리자 확인형은 운영자가 사유를 적어 승인/거절해요. 사유는 해당 회원에게 보여요. 승인할 때 정원·중복·수업 시작 여부를 다시 검사하고 예약 확정과 감사 기록을 함께 저장해요.

계정 연결은 해당 고객의 **기존 예약 내역도 보여 주는 권한 부여**예요. 동명이인과 이메일을 확인한 뒤 연결해야 해요. 직원 소속·지점 운영 권한은 생기지 않아요. 회원 연결을 회수하면 조회·신청이 차단되지만 기존 예약을 취소하지는 않아요. 남은 신청은 거절할 수 있고 승인할 수 없어요. 활성/회수된 연결의 재연결·다른 계정으로 교체는 아직 지원하지 않아요.

## 데이터와 신뢰 경계

| 위치 | 역할 |
| --- | --- |
| `db/migrations/0007_member_requests.sql` | 고객 계정 연결, 신청, 정책, 승인·철회·회수 함수 |
| `db/migrations/0008_member_cancellation.sql` | 회원 본인 예약 취소·버전·가능 여부 조회 |
| `db/migrations/0009_member_rescheduling.sql` | 같은 프로그램의 회원 회차 변경·정원·감사 |
| `db/migrations/0010_automatic_confirmation.sql` | 프로그램별 확정 방식·기대 정책 검사·즉시 확정 |
| `src/server/services/member-bookings.ts` | 서버 인증, 검증된 이메일, 제한된 DB 역할·세션 만료 검사 |
| `src/app/workspace/member-actions.ts` | 회원·관리자 Server Actions와 캐시 갱신 |
| `src/app/workspace/member/page.tsx` | 본인 회차·신청·예약 화면 |
| `src/components/bookings/member-administration.tsx` | 승인 대기·고객 연결·프로그램 정책 |

검증된 Auth 사용자 → 내부 사용자 → `app_private.customer_links` → 지점 고객 → `app.member_requests` → 승인 시 `app.bookings` 순서예요. 회원은 직원용 `withTenant` 소속을 갖지 않아요. 서버가 검증한 사용자 ID로 제한된 SECURITY DEFINER 함수만 호출하며 함수가 본인의 활성 연결과 조직·지점 상태를 확인해요. 클라이언트가 보낸 사용자 ID/이메일을 인증 근거로 쓰지 않아요.

코드는 SHA-256 해시만 저장하며 조회 API에 반환하지 않아요. runtime에는 private 연결 테이블·내부 권한 검사 함수 접근이나 직접 쓰기를 허용하지 않아요. 신청 테이블은 조직·지점 복합 FK와 강제 RLS를 적용하고 직원 조회는 배정된 지점으로 제한해요. 함수는 고정 search_path와 명시적인 EXECUTE 권한을 사용해요. Data API는 계속 꺼 두며 private 스키마를 공개하지 않아요.

고객 연결·회차·신청 행 잠금과 버전으로 중복 제출, 마지막 자리 승인 경합, 승인과 철회 경합을 처리해요. 승인이 실패하거나 감사 기록이 실패하면 예약과 신청 변경을 모두 롤백해요. 신청 키 재시도는 같은 신청을 반환해요.

## 제한과 다음 작업

- 연결별 대기 신청은 최대 20건, 회원의 회차·신청·예약 목록과 관리자 승인 대기는 각각 최대 100건이에요. 페이지 이동·검색은 후속 작업이에요.
- 지점당 한 계정은 한 고객에 연결돼요. 여러 지점 연결은 가능해요.
- 신청을 닫아도 이미 접수한 신청은 남아요. 신청 마감 이후에도 시작 전이고 정원이 있으면 운영자가 승인할 수 있어요.
- 확정 예약 변경·취소는 본인이 수업 시작 24시간 전까지 할 수 있어요. 변경은 같은 프로그램의 회원 신청이 열린 회차만 가능해요. 대기열·알림 발송·복구 가능한 재연결은 미구현이에요.
- 로그인 후 회원/운영 진입을 구분해요. Figma 파일 반영과 추가 모바일 상태 검증은 후속 작업이에요.

## 검증 (2026-10-15)

설정 7개 + DB 66개 = 총 73개 테스트, 타입·린트·Webpack 프로덕션 빌드 통과. 회원 테스트는 이메일 불일치·일회용 코드 경합·타인 조회/신청 차단·정원 경합·승인/철회 경합·감사 실패 롤백·초대 만료/회수·회원 접근 회수를 포함해요.

서울 개발 DB에 0007~0010를 적용했어요. `node scripts/verify-hosted-members.mjs PROJECT_REF`는 정확한 프로젝트를 확인하고 runtime으로 임시 연결·신청·승인·자동 확정·회원 변경/취소·접근 회수·RLS·감사를 검증한 뒤 전부 롤백해요. 실제 Auth 계정을 만들거나 이메일을 보내지 않아요. 실제 회원 계정 연결·신청/철회/재신청·관리자 승인·회원 결과 재조회 두 계정 브라우저 흐름도 완료했어요. 거절·회수 경합은 DB 테스트 범위예요. 공개 배포는 하지 않았어요.

실제 계정 검증 진행: 사용자 승인 후 개발 고객의 Gmail 회원 연결 코드를 발급했고, 개발 프로그램은 관리자 확인형·24시간 전 마감으로 열었어요. 새로고침 후 저장 확인 완료. 실제 Gmail 회원 연결 수락·기존 본인 예약 조회·10/20 신청/철회/재신청·새로고침 저장을 확인했어요. 회원으로 관리자 예약 URL 접근 시 404를 확인했어요. Naver 관리자에서 10/20 15시 신청을 승인했고 승인 대기 제거·예약 확정·정원 1/1·새로고침 저장까지 확인했어요. 당시 승인 1건·철회 1건이었으며 Gmail 회원 화면의 승인 완료·처리 사유·확정 예약·만석 신청 불가·새로고침 유지도 확인했어요.

초기 UI는 공통 토큰만 적용한 기능 검증 화면이었어요. 사용자 피드백 이후 아래와 같이 기존 Figma 구성을 적용했어요.

## 실제 데이터 화면 디자인 (2026-10-14)

Figma 회원 수업 `21:3`·내 예약 `21:220`의 모바일 폭, 시간 카드, 상태 배지, 하단 메뉴를 실제 데이터 화면에 적용했어요. 기존 StatusChip·Button·BottomSheet와 Lucide 아이콘을 재사용해요. 실제 기능이 없는 AI·알림 메뉴와 강사·강의실 샘플은 표시하지 않아요.

- **내 예약**: 다가오는 확정 예약, 승인 대기/철회, 지난 이용·취소, 접을 수 있는 처리 내역.
- **수업**: 날짜 필터, 시간·프로그램·잔여석 카드, 신청 확인 시트. 만석은 신청 불가.
- **내 정보**: 사업장 연결·연결 목록·운영 화면 이동·로그아웃.
- 관리자 예약은 Figma `182:2`를 기준으로 사이드바·필터·열별 목록을 적용하고 승인 대기·고객/회차·등록·설정을 별도 탭으로 나눴어요.

기존 화면을 실제 구현 범위에 맞춰 적용했으며 전체 데모 기능을 복제한 것은 아니에요. 회원 390px 화면·하단 메뉴·만석 카드를 확인했어요. 새 관리자 디자인도 실제 Naver 계정으로 목록·업무 탭·취소 검색·상세·검색 초기화·390px 모바일 배치를 확인했어요. 새 회원 신청 시트도 390px에서 제출·성공 안내·동일 요청 재제출 중복 방지·내 예약 반영·새로고침·철회까지 확인했어요. Figma 파일 자체는 수정하지 않았어요.

신청 시트 검증을 위해 10/22 15~16시 개발 회차(정원 1)를 생성했어요. 실제 Gmail 계정으로 신청·철회 검증을 완료했고 검증 신청은 철회 내역으로 남겼어요. 관리자 검색 초기화 뒤 선택값이 남는 문제도 수정해 전체 조건·목록 일치를 확인했어요.

## 로그인 후 진입

운영 조직이 있는 계정은 조직 선택 화면으로, 운영 소속 없이 활성 회원 연결만 있는 계정은 내 예약으로 이동해요. 소속·연결이 없으면 회원 예약 진입, 직원 초대 수락, 새 사업장 생성을 구분해서 안내해요. 회원의 내 정보 → 사업장 운영 화면은 `/workspace?mode=manage`로 열어 자동 이동을 건너뛰어요. 이 값은 화면 선택만 바꾸며 접근 권한을 부여하지 않아요. 로그인 목적지는 계속 고정된 내부 경로예요. 실제 Gmail 세션으로 기본 진입과 운영 화면 왕복을 확인했어요.

## 회원 직접 취소 (2026-10-14)

내 예약의 취소 버튼 → 하단 확인 시트 → 사유(1~200자)·확인 체크 → 취소 순서예요. 수업 시작 24시간 전까지, 출석이 미기록인 본인의 확정 예약만 가능해요. 서버가 활성 회원 연결·조직·지점, 예약 소유자와 기대 버전을 다시 검사해요. 연결→회차→예약 순서로 잠그고 취소와 실제 회원 행위자의 감사 기록을 원자적으로 저장해요.

타인 예약·회수된 연결·마감·잘못된 사유·오래된 버전은 거절해요. 관리자 취소/회차 변경과의 경합에서 한쪽만 성공하고 감사 저장 실패 시 취소도 롤백되는 것을 DB 테스트로 확인했어요. 원격 검증 역시 취소·잔여석·감사를 검사한 뒤 롤백했어요.

실제 Gmail 회원의 10/20 15시 개발 예약을 390px 화면에서 취소했어요. 성공 안내·취소 내역 이동·새로고침 저장·수업 잔여석 1자리 반환 확인 완료. 개발 예약은 총 4건(확정 2·취소 2), 신청 이력은 승인 1·철회 2예요. 기존 신청의 승인 이력은 예약 취소 후에도 유지해요. Figma 파일 변경·공개 배포는 없어요.

## 회원 직접 회차 변경 (2026-10-15)

내 예약의 변경 버튼 → 기존 일정 확인 → 새 회차·사유·확인 체크 → 완료 카드 순서예요. 신규 신청은 여전히 관리자 확인형이고, 이미 확정된 예약을 같은 프로그램 안에서 옮길 때는 다시 승인받지 않아요. 프로그램의 회원 신청이 닫혀 있으면 직접 변경도 닫혀요.

- 원래 회차와 새 회차 모두 시작까지 24시간 초과, 본인의 확정·출석 미기록 예약만 변경해요.
- 같은 지점·프로그램의 열린 회차만 허용해요. 만석, 이미 확정한 회차, 승인 대기 신청이 있는 회차는 거절해요. 목록은 기존 회원 조회의 최대 100회차 범위예요.
- 연결 권한을 재검사하고 두 회차를 UUID 순으로 잠근 뒤 예약 버전을 검사해요. 새 자리 확보·이전 자리 반환·회원 행위자 감사 기록은 한 트랜잭션이며 실패하면 기존 예약이 유지돼요.
- 예약 ID와 원래 생성 요청 ID는 유지해요. 이전 신청의 승인 이력도 원래 신청 회차를 그대로 가리켜요. 최신 일정은 내 예약에서 확인해요.

DB 검증에는 소유자/지점/프로그램 격리, 닫힌 정책, 양쪽 마감, 만석·중복·대기 신청, 감사 실패 롤백, 두 회원의 마지막 자리 경합, 관리자 변경/취소 경합, 회수된 연결 차단, 원래 생성 요청 재시도를 포함해요. 총 68개 테스트와 타입·린트·Webpack 빌드 통과, 서울 개발 DB 원격 검증은 전체 롤백했어요.

실제 Gmail 회원의 개발 예약을 10/21→10/22로 변경해 새로고침 저장·기존 자리 반환·새 회차 만석을 확인했어요. 완료 UI 개선 후 10/22→10/21로 복원하며 변경 전후 날짜·확정 완료 카드·입력 폼 제거까지 390px에서 검증했어요. 예약은 여전히 4건(확정 2·취소 2), 회차 4개예요. Figma 파일 수정·커밋·공개 배포는 없어요.

## 프로그램별 자동 확정 (2026-10-15)

관리자의 회원 신청 설정에서 신청 열기/닫기와 별도로 **관리자 확인 후 확정 / 신청 즉시 자동 확정**을 선택해요. 기존·신규 프로그램의 기본값은 관리자 확인이며, 기존 프로그램을 자동으로 바꾸지 않아요. 현재 프로그램 유형(그룹/기구/듀엣) 데이터가 없어 유형별 기본값 자동 선택은 후속 범위예요.

회원 수업 카드와 신청 시트에 확정 방식을 표시해요. 자동 확정은 즉시 확정 및 24시간 전 변경·취소 마감 확인 체크가 필요해요. 신청 마감을 2시간 전으로 정한 프로그램에서도 일반 취소 마감은 24시간 전을 유지해요. 대기열의 ‘자리 나면 자동 확정’ 및 그 예외 취소 정책과는 다른 기능이에요.

- 클라이언트가 본 확정 방식을 서버에 전달하고 현재 설정과 비교해요. 화면을 연 뒤 설정이 바뀌면 새로고침을 요구하며 의도와 다른 방식으로 처리하지 않아요.
- 자동 확정은 신청·예약·승인 결과·정원·감사를 원자적으로 저장해요. 회원의 실제 사용자 ID를 감사 행위자로 남기며 mode=automatic을 기록해요.
- 같은 요청 키는 같은 결과를 반환해요. 예약 취소 후 재전송해도 되살리지 않아요. 중복 예약과 기존 대기 신청이 있으면 새 신청을 거절해요.
- 설정 변경은 새 신청부터 적용해요. 기존 승인 대기를 자동 확정하지 않고, 대기 신청은 계속 운영자가 처리해요.
- 정책 변경 감사에는 변경 전후의 열림·마감·확정 방식을 남겨요.

설정 권한·지점 격리, 2/24시간 마감, 정책 변경 경합, 마지막 자리 동시 신청, 중복 재시도, 감사 실패 전체 롤백을 포함해 총 73개 테스트 통과. 서울 원격 검증은 롤백했어요. 실제 회원 390px 화면에서 10/22 자동 확정→새로고침 유지→취소를 확인했어요. 검증 프로그램은 관리자 확인·24시간 마감으로 복원했어요. 현재 개발 예약 5건(확정 2·취소 3), 신청 4건(승인 2·철회 2)이에요.

관리자 설정 UI의 실제 로그인 제출은 이번 범위에서 별도로 수행하지 않았어요. 설정 함수·권한은 DB 테스트와 제한된 runtime 개발 검증으로 확인했어요. 운영 배포·메일/문자 발송·Figma 파일 수정은 없어요.
